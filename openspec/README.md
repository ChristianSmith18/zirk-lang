# OpenSpec Authoring Policy

OpenSpec is repository-internal planning and conformance material. Proposals,
designs, tasks, delta specs, and main capability specs may retain the language
in which the accepted engineering change was reviewed (currently English or
Spanish). Normative keywords such as `SHALL`, `MUST`, `MAY`, scenario structure,
public Zirk identifiers, and code examples remain stable and unambiguous.

Public language specifications, handbook content, source code, diagnostics,
and generated website content are English. Archiving a Spanish working change
into a main OpenSpec capability does not turn that internal artifact into public
documentation and does not override the English canonical semantic documents.

When editing an existing capability, use English for new requirements unless a
coherent translation of the complete capability is part of the same reviewed
change. Do not mechanically translate isolated sentences in a way that creates
a mixed requirement or changes established terminology.

The current normative-source hierarchy is documented in
`docs/handbook/_editorial/source-map.md`.
