## Why

Every phase so far has left decision D9 (`fase-4a-errores`'s own design doc, reaffirmed in `fase-4b-excepciones` and `fase-4c-recursos`) in place: `Fn(P...) => R`/`Function(P...) => R` cannot be written in any type position, so a closure can only ever live in an inferred local — it can never be returned, stored in a field, passed as a typed parameter, or otherwise leave the frame that created it. `openspec/specs/zirk-callables/spec.md` already states the final behavior normatively (`Fn(String) => Result<User, ParseError>`, contravariant parameters, covariant results, a returned closure closing over a mutable counter) — none of it type-checks today; the parser rejects the annotation outright with `NOT_IMPLEMENTED` (`crates/zirk-parser/src/parser.rs`, `reject_function_type`).

This blocks more than callables on their own: `docs/init/ZIRK_ROADMAP.md` Phase 4d makes escaping closures the roadmap owner of this gap, and `docs/decisions/proximos-pasos-fase-4.md` (this session's own planning document) identifies closure escape as the single most important open question for ADR-003 (the memory-strategy decision) — it is exactly the pattern that would exercise a real choice between escape analysis and any alternative, and today it cannot be exercised at all because nothing can type a closure that escapes.

Investigation this pass (see `design.md`) found two different things bundled under "D9": a *representation* question and a *type-identity* question. The representation question is already solved — `zirk-ir/src/lower.rs`'s `lower_lambda` (decision D10, `fase-2`) copies every captured value out of the enclosing frame *at closure-creation time*, into a flat `{function pointer, capture...}` struct; there is no pointer back into the creating frame to invalidate, so a closure is already safe to escape at the representation level. The type-identity question is real and unsolved: today every lambda literal gets its *own*, non-interned `Base::Function`/`IrType::Closure` id (`declare_class`'s sibling for lambdas, `checker.rs` line ~6698: "each lambda gets a type of its own... two lambdas of the same shape are not interchangeable"), specifically because its captures are part of its representation — two differently-captured closures have two genuinely different LLVM struct layouts. A fully polymorphic `Fn(...) => R` (any matching closure assignable to it, from any branch, at any point) needs those different layouts erased behind one uniform, heap-boxed representation — a real new codegen mechanism, not a checker unblock.

This proposal deliberately does **not** build that general mechanism (see "Explicitly out of scope"). It ships the part that does not need it: `Fn(...) => R` as a real annotatable type, satisfied by a named function or a capture-less lambda (both already structurally interned today, already uniform — no boxing needed), and by a *single* capturing closure literal written directly at the annotated position (no boxing needed either, because the checker can keep that position's static type as that one literal's own exact `Base::Function` id instead of erasing it).

## What Changes

- `Fn(P...) => R`/`Function(P...) => R` parseable and type-checked in every position `zirk-callables`' spec requires: parameter types, return types, field/attribute types, generic type arguments, and local variable annotations — with parameter labels, `name?: T` optional parameters, and `...values: T` variadics.
- A named function, or a capture-less lambda, type-checks against — and freely interchanges with any other of the same shape at — a compatible `Fn(...) => R` position: contravariant parameters, covariant result, matching labels/optionality/variadic shape. Both are already structurally interned/uniformly represented today (`Checker::intern_fn_type`, an empty-captures `ClosureLayout`), so this direction needs no new representation.
- A *single* capturing closure literal, written directly at a `Fn(...) => R`-typed position (a local's initializer, an argument at its call site, a `return` expression, a field initializer), also type-checks and escapes — the position's static type stays that literal's own exact `Base::Function` id rather than the general callable type, so nothing needs boxing. `invalid_closure_returned_from_a_function` and `invalid_generic_inference_from_a_closure_argument` (`crates/zirk-sema/tests/typing.rs`), both accepted-as-rejections purely because D9 made the annotation itself impossible, become accepted for this shape.
- Recursive lambdas work when given an explicit `Fn(...) => R`-typed binding (`ZIRK_LANGUAGE_SPEC.md` section 6: "Recursive lambdas require an explicit binding type") — the single-literal case above.
- `is` becomes valid between two callable values (identity: same underlying function, same captured values) — closures currently reject `is` with "has no identity to compare" (E0403), which contradicts `CORE_LANGUAGE_SEMANTICS.md`'s own "callable identity uses `is`". `==`/`!=` remain rejected, unchanged (already correct today).
- A new diagnostic when a `Fn(...) => R` position would need *more than one* distinct capturing closure (two different `return` statements each returning a different capturing literal, reassigning a variable from one capturing literal to a differently-captured one, …): rejected with a clear message that general callable-type polymorphism across differently-captured closures needs a boxed representation this pass does not build, instead of silently producing an unsound program.

### Explicitly out of scope

- **General callable-type polymorphism**: a `Fn(...) => R` position that must accept two or more *differently-captured* closures (across branches, reassignment, or a collection element type) needs the captures heap-boxed behind a uniform calling convention — a real new codegen mechanism (see `design.md`). Flagged with a dedicated diagnostic rather than attempted; a natural next slice once this one is verified.
- **A captured binding written by the closure, lifted into one shared cell** (`CORE_LANGUAGE_SEMANTICS.md`'s own fourth capture rule) — today rejected outright (`E0417`, "cannot reassign inside a closure... capture is by value"). This needs its own new mechanism (boxing the captured *slot* so both the creating frame and the closure read/write through the same heap cell) independent of the polymorphism question above.
- **`.clone()` deep-cloning a closure's environment** — meaningfully different from an ordinary copy only once shared mutable cells exist to deep-clone; with only snapshot/whole-reference captures (this pass's scope), copying a closure value is already a correct, complete clone, so there is nothing distinct to build yet. Revisit once the lifted-cell mechanism above lands.
- **A captured projection as an independent deep snapshot** (the third capture rule) — investigated, not changed: Zirk's ordinary projection-read semantics already produce an independent value at the read site (roadmap Phase 2/3), and `lower_lambda` captures by reading the slot's current value, so this rule is expected to already hold without new code. Verified with a real program in this pass's own manual testing, not assumed.
- **Callable-type compatibility for mutability/safety/permission-decorated functions** (`zirk-callables` spec's own "mutability, safety, and permissions are compatible" clause) — permissions do not exist as a runtime concept yet (Phase 6); nothing to check yet, so nothing changes here.
- **`Fn(...) => T throws X`** — not part of the callable-type grammar `ZIRK_LANGUAGE_SPEC.md`/`CORE_LANGUAGE_SEMANTICS.md` actually specify; there is no such syntax to enable.
- **Multiple declarations and simultaneous assignment** (the other Phase 4d roadmap bullet) — unrelated code paths (grammar/checker/IR for `mut a, b: T = x, y;` and `left, right = right, left;`, nothing to do with callable types or closures); tracked as its own separate change so each stays independently reviewable.

## Impact

- Specs affected: `zirk-callables` (implements its core assignability/escape requirement; identity/mutable-capture/clone remain partially open, tracked in feature-status), `zirk-grammar`, `zirk-type-system`.
- No breaking changes: every program that compiles today keeps compiling: this only makes new positions and comparisons valid that previously reported `NOT_IMPLEMENTED`/`E0403`/`E0417`, never valid that is now rejected.
