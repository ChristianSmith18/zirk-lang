## 2. Lexical

- [x] 2.1 Integer literals with a suffix or width inference, per whatever the existing grammar already distinguishes — resolved by deliberate omission: the lexer never had (and still does not have) a suffix family for integers parallel to `Float`'s (`FLOAT_WIDTHS`) — any suffix after a decimal integer that is not a `Float` width or a duration unit was, and still is, a lexical error (`INVALID_NUMERIC_SUFFIX`). An integer literal's width is decided only by explicit context: `as` (task 4.3) or the destination of a contextual conversion (`Int64(3 + 4)`, task 7). *Implicit* width inference from a simple assignment destination (`mut x: Int8 = 5;` typing `5` as `Int8` with no `as`) is out of scope, explicit debt — see 13.4

- [x] 2.4 `{expr}` inside a `String` literal, with `\{`/`\}` as escapes — found already implemented in the lexer before this phase (`TokenKind::InterpolatedStr`/`StrPart`, with brace-depth counting so a nested expression with its own braces does not close the interpolation early, and the escape already recognized); nothing to do here, just confirm and stop gating it in the parser (3.2)

## 3. Grammar

- [x] 3.1 Bitwise and shift operators (`&`, `|`, `^`, `~`, `<<`, `>>`), at the precedence levels the spec fixes, distinct from `&&`/`||` — its own precedence decided during implementation (the roadmap does not fix exact numbers): bitwise between comparison and additive, shift tighter than the other three, the same relative order as C/Rust/Swift (`Or=1, And=2, Eq/Is=3, Compare=4, Coalesce=5, BitOr=6, BitXor=7, BitAnd=8, Shl/Shr=9, Add/Sub=10, Mul/Div/Rem=11`). The lexer already had every token (`Amp`, `Pipe`, `Caret`, `Tilde`, `Shl`, `Shr`, and their `=` forms) modeled before this phase, with its own `Phase::THREE_B` gate in `TokenKind::phase()` — removed for this family (not for `**`, which still awaits `Float`)
- [x] 3.2 AST for an interpolated expression: literal text plus a list of sub-expressions, preserving the order of appearance — new `Expr::Interpolated(InterpolatedStrExpr)`, with `parts: Vec<InterpolatedPart>` (`Literal(String)` | `Expr(Expr)`). The parser removes its own gate (`pending_literal`) and re-lexes each `{expr}` separately — the lexer stores the raw text instead of tokenizing it inline precisely for this (`StrPart::Expr`'s own doc comment) — shifting each resulting span by the offset where the interpolation starts, so a diagnostic inside `{expr}` points at the file's real location instead of position 0 of a text that nobody wrote as its own file
- [x] 3.3 Tests: one valid and one invalid case per new rule — done for bitwise/shift (`crates/zirk-cli/tests/corpus/valid/bitwise_and_shift.zrk`, `invalid/bitwise_on_non_integer.zrk`, plus `typing.rs`) and for interpolation (`valid/string_interpolation.zrk`, `invalid/interpolation_of_non_printable.zrk`, plus tree shape in `grammar.rs` and types in `typing.rs`)

## 4. Types — integer widths

- [x] 4.1 Register `Int8`/`Int16`/`Int64`/`Int128` and the complete `UInt8`…`UInt128` family as checker types — `Base::Int32` generalized to `Base::Int(IntWidth)`, with `IntWidth` (width + signedness, not ten variants: LLVM already models any width natively via `IntType`) in `zirk-sema/types.rs`, and an independent copy in `zirk-ir/ir.rs` for the same reason `IrType` is already independent of `zirk_sema::Type` (the boundary that ships a `.zpkg` must not move when the frontend changes). `Type::INT32` — already an existing alias of `Type::of(Base::Int32)` — became `Type::of(Base::Int(IntWidth::I32))`, which left ~13 checker sites that used the constant untouched; the ~43 IR/backend sites that used the variant directly needed the mechanical change (`sed` plus manual cleanup)
- [x] 4.2 Checked arithmetic per width and signedness, reusing Phase 1's `Int32` mechanism (see 1.1) — `checked_arithmetic` reads the operand's real `IntType` (`left.get_type()`) instead of assuming `i32_type()`, and the caller picks the intrinsic (`sadd`/`uadd`, etc.) based on signedness; `checked_division` generalized with the same pattern, with the `MIN / -1` case checked only when the width is signed (does not apply to `UInt`) and `MIN`'s bit pattern built with `const_int_arbitrary_precision` because `Int128::MIN` does not fit in a single `u64` — a naive `1u64.wrapping_shl(bits-1)` is wrong for `bits=128`, found and fixed while testing a real program; comparisons (`Lt`/`LtEq`/`Gt`/`GtEq`) dispatch to signed or unsigned predicates depending on signedness, with a new checker check that both operands share a width (arithmetic already required it, comparison did not)
- [x] 4.3 Unambiguous implicit widening; narrowing, sign change, and any lossy conversion, always explicit — `Type::accepts()` extended: same signedness and `dst.bits() >= src.bits()` is implicit, any other case requires `as`. `as` between any two integer widths was implemented with no runtime check, Rust-`as` style (truncate/extend with or without sign, no range limit) — a decision made during implementation upon noticing that no value outside `Int32`/`Int64`/`Int128` could be constructed in a real program without going through explicit narrowing or sign change (a literal always types as `Int32`, and only same-sign widening reaches a larger width implicitly); the "safe" conversion the spec suggests via constructor/`Result` is deferred until `Result` exists (Phase 4). New `InstKind::IntCast` in the IR; the backend picks `build_int_s_extend`/`build_int_z_extend`/`build_int_truncate` based on source/destination width and the source operand's signedness, with no instruction when the width does not change. Two real bugs were found and fixed while verifying with compiled programs: (a) `lower_expr_as` typed the widening but did not actually lower it — it silently let any `Int` to `Int` through without emitting the conversion, handling only `Object`/`Contract`; (b) the IR verifier rejected a valid shift (`UInt32 << Int32`) because it required `left_ty == right_ty` for every `BinaryOp` with no exception — shift allows the amount to have an independent width (see 4.4), so `Shl`/`Shr` were exempted from that equality
- [x] 4.4 Bitwise/shift operators on integers — generalized to all ten widths (previously only `Int32`, see earlier commit). Bitwise (`&`/`|`/`^`) requires the same width, same as arithmetic; shift (`<<`/`>>`) allows an amount with a width independent from the shifted value — an intentional asymmetry that forced the 4.3(b) fix in the verifier. `checked_shift` generalized: the limit is computed from the shifted value's width but compared using the zero/width constants of the amount's own type (not the value's), and the negative-amount check only applies if the amount has a signed width — a `UInt` amount is never negative, checking it as signed would have compared with the wrong predicate. Whether the right shift is arithmetic or logical is decided by the shifted value's signedness, not the amount's. Unary `-` now explicitly requires a signed width (message: "the `-` operator requires a signed number"); `~` accepts any width. Verified with a real program compiled and run, including the failure path (shift by an out-of-range amount)
- [x] 4.5 Tests: one valid and one invalid case per new rule — `integer_widths.zrk`/`.out` (arithmetic on `Int8`, comparison on `UInt8`, `Int32→Int64→Int128` widening chain, bitwise/shift with an independent-width amount, unary `~`, checked division/remainder), `integer_narrowing_not_implicit.zrk` (compile-time rejection of `Int32→Int8` with no `as`); in `zirk-sema/tests/typing.rs`: safe implicit widening, non-implicit narrowing, non-implicit sign change, explicit narrowing with `as`, explicit sign change with `as`, arithmetic between different widths rejected, negation of an unsigned width rejected, `~` on an unsigned width accepted, a shift amount of a different width accepted

## 5. Types — `Float`

- [x] 5.1 Register `Float16`/`Float32`/`Float64`/`Float128`, with `Float` as an alias of `Float64` — `Base::Float(FloatWidth)` in `zirk-sema/types.rs`, same pattern as `Base::Int(IntWidth)` (width as data, not one variant per width: LLVM already models every `FloatType` natively). `Type::FLOAT64 = Type::of(Base::Float(FloatWidth::F64))` is `Float`'s alias. The literal (`1.5`, `1.5f32`, `6.02e23`) was already fully modeled in the lexer before this phase (`TokenKind::Float(NumberLit)`, with an optional `f16`/`f32`/`f64`/`f128` suffix) — it was only gated in the parser; new `ast::Expr::Float(FloatLit)` that keeps the text unparsed (justified the same way `NumberLit` already is: a `Float128` value can exceed what the host's `f64` represents exactly, so parsing here would decide, at the wrong layer, a precision the destination type must not lose) — `zirk-codegen-llvm` parses that same text once, already at its destination width, through LLVM's own literal parser (`const_float_from_string`), never through a Rust `f64` in between. The checker validates the literal's range against the destination width with its own `f64` parse (`check_float_literal`) — deliberately not applicable to `Float128`, whose true range exceeds what an `f64` can represent without giving a false result; documented as a known gap, not a silently incorrect check. Implicit widening between `Float` widths (`Type::accepts`): always exact regardless of signedness (unlike integers, there is no sign crossing to decide), so the only condition is `dst.bits() >= src.bits()`. Narrowing and conversion with an integer, explicit with `as` — same unchecked mechanism as integers (new `InstKind::FloatCast`/`IntToFloat`/`FloatToInt` in the IR, `fptrunc`/`fpext`/`sitofp`/`uitofp`/`fptosi`/`fptoui` in the backend)
- [x] 5.2 Explicit infinities as valid values; identify every operation that under IEEE 754 would produce `NaN` and flag it for the runtime check (design: which operations need the check, not just which exist) — D2 from `design.md` followed as written: a result that overflows to infinity (`1.0 / 0.0`, a multiplication whose magnitude exceeds the width) is a valid value and is not checked; only a result IEEE 754 defines as `NaN` (`0.0 / 0.0`, `Infinity - Infinity`, `Infinity % x`, …) aborts. The check does not distinguish per operator which can produce `NaN` and which cannot — that would be a fragile table, redundant against the general IEEE 754 property that `x != x` is true if and only if `x` is `NaN` (`fcmp uno`, no dedicated intrinsic) — so it is applied uniformly after `Add`/`Sub`/`Mul`/`Div`/`Rem`, never before: `check_not_nan` in `zirk-codegen-llvm/src/emit.rs`, new runtime symbol `zirk_rt_float_nan` (same controlled-failure pattern as `zirk_rt_overflow`/`zirk_rt_invalid_shift`). `-x` (unary) does not need the check: flipping the sign bit cannot turn a non-`NaN` input into `NaN`
- [x] 5.3 Mixed integer/`Float` arithmetic produces `Float` — `native_arithmetic` gains a `(Base::Int(_), Base::Float(f), …) | (Base::Float(f), Base::Int(_), …)` arm that resolves to the already-present `Float` width, in either operand order; lowering (`lower.rs`, `ast::Expr::Binary`'s generic `match`) inserts `InstKind::IntToFloat` on the integer operand before emitting `InstKind::Binary`, so the verifier finds both operands already matching — no other operator the checker lets reach that general branch (comparison, bitwise, shift, equality) mixes widths, so the conversion never fires for them
- [x] 5.4 Tests: one valid and one invalid case per new rule, including at least one `NaN`-avoided-at-runtime case — `float_family.zrk`/`.out` (every width with its suffix, widening chain, explicit narrowing, mixed arithmetic in both orders, Int↔Float conversion, unary `-`, remainder, division by zero producing infinity), `invalid/float_literal_overflow.zrk` (a literal out of `Float16`'s range, rejected at compile time — the runtime `NaN`, `0.0 / 0.0`, was manually verified with a real program, exiting with the expected code 70, but does not go into the invalid corpus for the same reason `integer_narrowing_not_implicit.zrk` was renamed: the invalid-corpus harness compares the *compile-time* diagnostic's format, not a runtime abort); in `zirk-sema/tests/typing.rs`: safe widening between `Float` widths, non-implicit narrowing, explicit narrowing with `as`, explicit Int↔Float conversion, valid mixed arithmetic, arithmetic rejected between different `Float` widths, comparison rejected between `Int` and `Float`, valid unary negation, `~` rejected on `Float`.
  **Debt found and recorded, not resolved here:** `Float128` was excluded from `float_family.zrk` after it crashed the `windows-x86_64` CI runner with an access violation (not an assertion failure) — LLVM lowers `fp128` arithmetic to calls into a software library (`__addtf3` and similar) that the MSVC toolchain this project's Windows CI uses does not provide the same way `glibc`/`libSystem` do on Linux/macOS. `Float128` remains registered as a type, resolves, types, and its rules are checked in `zirk-sema/tests/typing.rs` (with no native code execution); what is not verified end to end on all four platforms is the `fp128` arithmetic itself. Investigating MSVC's software floating-point support linkage (or deciding that `Float128` on Windows is out of scope) is future work, not part of this task.

## 6. Types — `Char`

- [x] 6.1 Register `Char` as a checker type — `Base::Char` in `zirk-sema/types.rs`, its own `IrType::Char` in `zirk-ir` (does not reuse `IrType::String` directly — see 6.2/ADR-014). The `'...'` literal was already fully modeled in the lexer before this phase (`TokenKind::Char(String)`, storing the raw content between quotes without deciding whether it is exactly one grapheme — that is semantics, not lexing, by the lexer's own explicit design); it was only gated in the parser. New `ast::Expr::Char(CharLit)`. The checker validates with real Unicode segmentation (`unicode-segmentation` crate, UAX #29) that the content is exactly one extended grapheme — neither zero nor two or more —, new code `E0432`/`INVALID_CHAR_LITERAL`; verified with a real extended grapheme cluster (`'👨‍👩‍👧‍👦'`, a ZWJ-joined emoji sequence, several code points) accepted, and `'ab'`/`''` rejected. `Char` has no identity (`is` is rejected, unlike `String`) nor a default value (`docs/handbook/11-reference/03-built-in-types.md`: "invalid without an explicit value") — neither needed new code, both already excluded `Char` simply by not being on their lists
- [x] 6.2 Resolve the open representation question (design.md) before fixing how a literal or the element of iterating a `String` is typed — resolved as [ADR-014](../../../docs/decisions/ADR-014-representacion-de-char.md): `Char` shares `String`'s opaque representation (ADR-005) at the runtime/LLVM level — same opaque pointer, same `zirk_str_from_utf8` constructor, same `zirk_str_eq` comparison —, but is a distinct static `IrType::Char` (new `InstKind::ConstChar` instruction, parallel to `ConstString` rather than reusing it, so the verifier keeps distinguishing one value from another by the instruction that produced it). The option of an inline buffer with an escape was discarded (it duplicates the machinery `String` already has, for an unmeasured gain), as was restricting `Char` to a single code point (contradicts spec section 3 as written, with no real justification to reopen it)
- [ ] 6.3 `for ... in` over `String` produces `Char`, retiring the debt noted since Phase 2 — deliberately out of scope for this pass: it requires real iteration machinery (runtime grapheme segmentation inside `zirk-runtime`, plus the iterator protocol that today only exists for a user class's `Iterable<T>`), which is its own piece, not a minor extension of 6.1/6.2. `element_type`'s `Base::String` arm's message was updated to reflect that `Char` now exists — it went from "not implemented, arrives in Phase 3b" (`PENDING_FEATURE`) to "the grammar and type rules exist, lowering does not" (`NOT_LOWERED`), the same pattern as anything else in this checker that is built but not compilable
- [x] 6.4 Tests: one valid and one invalid case per new rule, including an extended grapheme of more than one code point — `char_literals.zrk`/`.out` (equality between equal and distinct `Char`s, a non-ASCII code point, a real extended grapheme cluster), `invalid/char_literal_multiple_graphemes.zrk` (`'ab'`, rejected at compile time); in `zirk-sema/tests/typing.rs`: single-code-point literal, extended-grapheme literal, more-than-one-grapheme literal rejected, empty literal rejected, valid equality, `is` rejected for lack of identity, plus the `for ... in` over `String` test updated from "pending on phase" to "not lowered yet"

## 7. Types — deep contextual conversion

- [x] 7.1 An explicit constructor (`Float(expr)`, `String(expr)`, …) establishes context over the compatible operator tree it directly contains — new syntax recognized in `check_call`/`lower_expr`'s `Call` branch: when the callee is a `Path` naming a native scalar with a conversion domain (any `Int`/`Float` width, or `String` — not `Boolean`/`Char`, which the spec does not exemplify with this mechanism) and is not shadowed by a local variable, it is treated as a contextual conversion instead of a class construction or a function call; decided before class construction because a native type name can never collide with one (type names are reserved). The "compatible tree" is arithmetic (`+ - * / %`, plus unary `-`) for a numeric destination, and only `+` for `String` — `*` with `String` needs no context because `String * Integer` is already native
- [x] 7.2 The context converts operands before operating, not the result afterward — verified with a real program: `Float64(3 / 4)` gives `0.75`, not `0.0` (which would be the result of dividing as `Int32` and converting afterward); `Int64(2000000000 + 2000000000)` gives `4000000000`, a sum that would overflow `Int32` if added first and widened afterward
- [x] 7.3 The context does not mutate the original operands nor cross into a function called inside the expression — neither needed dedicated code: the tree is never rewritten, it is walked twice with the same shape (once when checking, once when lowering) without touching the nodes; and a call is never one of the recognized forms (`Binary`/`Unary` with a compatible operator), so it is always a leaf — the context stops there by construction, not by a special case. Verified with a real program: `Float64(half(3) + 0.5)` computes `half(3)` as its own declared `Int32` (`3 / 2 = 1`), and only the result is converted at the boundary, before adding — it gives `1.5`, not what it would give if `half`'s own body had been rewritten to divide in `Float64`
- [x] 7.4 Decide whether the context crosses an operator overloaded via contract (design.md, open question) and verify it — resolved exactly as `design.md` proposed: it does not cross. No special case was needed to achieve this: recognizing a "compatible tree" only decides by syntactic shape (`Binary`/`Unary` with the correct operator) plus the destination's family (numeric or `String`) — it never inspects the operands' real type to decide whether to recurse. A class-typed operand is never numeric or `String` by itself, so any `Binary` node whose operand is a class falls outside the compatible tree from the context's perspective — it is checked/lowered normally (including dispatch to `_add`/etc. if the class declares it), and only the *result* is converted at the boundary, exactly the same treatment as any other call
- [x] 7.5 Tests: one valid and one invalid case per new rule — `deep_context_conversion.zrk`/`.out` (literal leaves, variable leaves, `String` concatenation, any numeric destination not just `Float`, unary `-`, a call as a boundary), `invalid/context_conversion_incompatible_leaf.zrk` (`Boolean` inside a `Float64` context, rejected at compile time); in `zirk-sema/tests/typing.rs`: conversion over arithmetic, over concatenation, toward any numeric destination, over unary negation, boundary at a call, incompatible leaf rejected, wrong argument count rejected

## 8. Types — `to_string()` and interpolation

- [x] 8.1 Confirm the contract's exact name and convention (design.md, open question) against `ZIRK_LANGUAGE_SPEC.md`/`ZIRK_STDLIB_SPEC.md` — resolved: `to_string()`, public, without the reserved underscore of operator contracts (`_add`, `_subtract`). `ZIRK_LANGUAGE_SPEC.md` section 4 explicitly reserves that underscore for operators ("Operators may only be overloaded through contracts... reserved methods such as `_add` and `_subtract`"); `to_string` is not an operator, and `ZIRK_STDLIB_SPEC.md` section 3 names it with no prefix ("every printable value uses `to_string(): String`") and describes it as something user code also calls directly, which the reserved prefix exists precisely to prevent for operators
- [x] 8.2 Register `to_string()` as a reserved contract, in the same family as Phase 3's operator contracts — with no formal contract table, using the same structural dispatch operators already use (decision D6): `Checker::is_printable` looks up `fn to_string(): String` by name and signature in the class's already-flattened method table (inherited included), exactly as `check_arithmetic` looks up `_add`. No new `ContractType` is needed because operator contracts do not have one either — the "contract" is the signature, not a registration
- [x] 8.3 Native implementation of `to_string()` for every scalar (the ten integers, `Float`, `Boolean`, `Char`, `String`) — the ten integer widths (`zirk_str_from_i8`…`zirk_str_from_u128`, with `Int128`/`UInt128` crossing the runtime boundary by pointer instead of by value: there is no stable `extern "C"` calling convention for a 128-bit integer by value across platforms — MSVC does not even have a native 128-bit integer type — so a local `alloca` holds the value and only its address crosses), `Boolean` and `String` (already existed), `Char` (no runtime call: it shares `String`'s representation bit for bit, ADR-014, so "converting" is just retitling the same pointer). **`Float32`/`Float64` yes, `Float16`/`Float128` no:** neither is a stable Rust primitive type on this toolchain (`f16`/`f128` are still behind an unstable feature), so there is no `Display` to fall back on without a manual decimal conversion this task does not build — a real, documented gap, consistent with the portability gap `Float128` arithmetic already has on Windows. The textual representation of an infinity (`inf`/`-inf`, what Rust's `Display` already produces) is not fixed by the spec; it was adopted as is for being the simplest practical value, revisable without breaking anything new
- [x] 8.4 A user type (class, record, enum) can implement `to_string()` — class and record already work (they share the same flattened method table, the lookup does not distinguish). An enum is out of scope: enums have no method table at all yet (`EnumType` has no `methods` field, unlike `ClassType`) — this is not new debt from this task, it is that enum methods in general do not exist yet
- [x] 8.5 `print`/`println` route through `to_string()`; retire `require_printable` and its closed list — `require_printable` stays (it is still where the error is reported), but its closed list (`Int32`/`Boolean`/`String` only) was replaced with `Checker::is_printable`, which decides structurally for any printable native scalar or a class/record with `to_string()`
- [x] 8.6 Desugar `"{expr}"` into literal text concatenated with `expr.to_string()` — the shape of the lowering already existed (`lower_interpolated`, a chain of `InstKind::Concat`) and now shares a single conversion point with `println` (`lower_to_string`, new): a native scalar lowers to `InstKind::ToString` (which the backend dispatches by the operand's already-recorded width/signedness, the same pattern `is_signed`/`emit_binary` already use), a class/record with its own `to_string()` lowers to a real method call (`Call`/`CallVirtual`, the same shape as any other method call, `lower_method_call`) — because a real conversion needs to resolve a symbol or a table, something `InstKind::ToString` alone cannot express
- [x] 8.7 Tests: one valid and one invalid case per new rule — `to_string_contract.zrk`/`.out` (every integer width, `Float32`/`Float64`, `Char`, interpolation of the same, a class with `to_string()` printed directly and via interpolation, `Int128`/`UInt128` with a real magnitude over 64 bits verified against an exact calculation in Python), `invalid/float16_not_printable.zrk` (`Float16` rejected at compile time); in `zirk-sema/tests/typing.rs`: printing the new scalars, `Float16` printing rejected, printing a class with a valid `to_string()` (direct and interpolated). Phase 1's original `.zrk` (`printing.zrk`, only `Int32`/`Boolean`/`String`) was left untouched — it stays green, and separating this phase's new scope into its own file avoids mixing one phase's coverage with another's
