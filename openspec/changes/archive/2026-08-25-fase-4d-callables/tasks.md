## 2. Chequeador — tipo callable real

- [x] 2.1 `resolve_written_type` (o su equivalente) construye un `Base::Function`/`FnType` real desde la anotación escrita, reutilizando `Checker::intern_fn_type` (interning estructural, ya existe) — no el camino no-interned que usan hoy los lambdas
- [x] 2.2 Compatibilidad contravariante en parámetros / covariante en resultado, con labels/opcionalidad/variadic coincidentes, para: función nombrada, lambda sin capturas, método bound/unbound — implementado para función nombrada y lambda sin capturas (`Checker::fn_shapes_compatible`/`callable_assignable`); método bound/unbound no ejercitado (sin caso de uso real en el corpus de esta pasada, mismo camino estructural aplicaría)
- [x] 2.3 `expect_assignable`: una función nombrada o lambda sin capturas hacia una posición `Fn(...) => R` se acepta estructuralmente (D12) — retirar o acotar el rechazo actual de "cada closure tiene su propio tipo" para este caso específico, sin tocar el rechazo entre dos closures con capturas distintas
- [x] 2.4 D14: un closure con capturas satisface una posición `Fn(...) => R` solo cuando el literal aparece directamente en esa posición — **acotado tras la implementación real** a inicializador de local (`check_let`) y expresión de `return` (`check_return`), los dos únicos casos donde una sola posición sintáctica estática respalda el mecanismo con solidez; argumento en sitio de llamada y valor de campo NO se soportan en esta pasada (ver addendum de `design.md`) — se rechazan con el mismo diagnóstico nuevo, no con un panic
- [x] 2.5 D14: el tipo de retorno declarado de una función que es un `Fn(...) => R` con capturas exige que todo `return` que produzca un `Base::Function` remita al mismo literal (mismo span/id) — dos literales distintos se rechazan con un diagnóstico nuevo y claro (`E0439`), no `TYPE_MISMATCH` genérico
- [x] 2.6 D14: reasignar un local `Fn(...) => R` de un literal con capturas a uno distinto se rechaza con el mismo diagnóstico — acotado a la reasignación desde un local YA inicializado con un literal; un `mut f: Fn(...) => R;` sin inicializador seguido de una asignación con capturas también se rechaza (nunca se soporta adopción vía asignación simple, solo vía inicializador — ver addendum de `design.md`)
- [x] 2.7 `invalid_closure_returned_from_a_function` e `invalid_generic_inference_from_a_closure_argument` (`crates/zirk-sema/tests/typing.rs`) pasan a ser casos válidos para la forma de un solo literal (renombrados `valid_closure_returned_from_a_function`/`valid_generic_inference_from_a_closure_argument`); añadido `invalid_two_differently_captured_closures_in_one_return_type` como el caso que sigue rechazado
- [x] 2.8 `is` entre dos valores callable se acepta (D15); `==`/`!=` siguen rechazados sin cambios — test de ambos
- [x] 2.9 Lambda recursiva con tipo de binding explícito (`mut fact: Fn(Int32) => Int32 = (n: Int32): Int32 => ...;`) — test manual con un programa real (`callable_types.zrk`); requirió un mecanismo nuevo no cubierto por D12–D15 (ver addendum de `design.md`): pre-declaración del binding antes de chequear su propio inicializador, y en IR una auto-llamada directa en vez de una captura real. Encontrado en revisión: usar el binding recursivo como valor (no como callee directo) panickeaba en `zirk-ir` en vez de rechazarse en el checker — corregido con una caminata del AST del cuerpo (`Checker::check_recursive_reference`) que rechaza toda aparición que no sea el callee directo de un `Call`, incluida una alcanzada desde una lambda anidada (`E0440`)
