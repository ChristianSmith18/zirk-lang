## Context

`fase-4b-excepciones` built the full propagation mechanism (D1: pending `thread_local` slot; D2: `try_stack` with direct dispatch to an active `catch`; D3: `finally` duplicated at each exit) for explicit `throw`/`try`/`catch`. Its own `design.md`, section D5, investigated and deliberately deferred extending that mechanism to the native safety failures, documenting three concrete gaps (not just "no time"):

1. The checks live in `zirk-codegen-llvm/src/emit.rs`, a layer below where `zirk-ir` still has any notion of `try`/`catch` (that control flow has already been compiled into flat `Jump`/`Branch` terminators before reaching codegen).
2. A native failure never appears in a declared `throws` (by language design), so `lower_throws_check` cannot keep running only conditionally after `throws`-declared calls.
3. Nothing today synthesizes a *real* (non-stub) method body for a natively injected class — everything registered that way so far is either abstract-and-never-instantiated (`Error`/`Throwable`/`RuntimeError`) or body-less (`StackTrace`, a single `Alloc`).

This change tackles all three, scoped to the four checks D7 marked as tractable (division by zero, invalid shift, invalid repeat, `NaN`), leaving overflow and invalid cast out.

## Goals / Non-Goals

**Goals:**
- The four tractable native failures are real `RuntimeError` objects, catchable by concrete type, by `RuntimeError`, or by `Throwable`, with `message()`/`code()`/`cause()`/`stack_trace()` genuinely working.
- The check itself (the comparison that decides whether the failure occurs) moves to `zirk-ir`; codegen triggers the exception the same way it triggers any other `InstKind::Throw`.
- An uncaught program still aborts with a nonzero exit code — the visible behavior for a program that never uses `try`/`catch` does not change.

**Non-Goals:**
- `OverflowError`, `InvalidCastError`: out of scope (see `proposal.md`).
- No change to `checked_arith`'s own overflow mechanism nor to `zirk_rt_check_cast`.
- No new crate dependency: `zirk-ir` does not gain a dependency on the parser or lexer.

## Decisions

**D8 — the four new classes' method bodies are hand-built as IR, inside `zirk-ir::lower()`, without going through the parser.** A "prelude" approach was considered (and rejected): parsing a real Zirk source fragment with the four classes and merging it into the user's `Program` before checking, which would give them fully ordinary bodies with no special case at all. Rejected because `zirk-sema` does not depend on `zirk-parser`/`zirk-lexer` today (only as `dev-dependencies`, for its own tests) — turning that into a real build dependency is a bigger architectural-layering change than this piece warrants, and further, the injection point would have to live at every call site of `zirk_sema::check` (the real CLI and every `zirk-ir`/`zirk-sema` test helper that builds its own `Program` today), duplicating the problem instead of solving it once.

Instead, each of the four classes has exactly one field (`reason: String`) and four trivial methods — building them by hand is tractable:
- `construct(reason: String) { this.reason = reason; }` — an `Alloc` plus a `StoreField`.
- `message(): String { return this.reason; }` — a `LoadField` plus a `Return`.
- `code(): String { return "<FIXED_CODE>"; }` — one string constant per class (`E_DIVISION_BY_ZERO`, `E_INVALID_SHIFT`, `E_INVALID_REPEAT`, `E_FLOAT_NAN`) plus a `Return`.
- `cause(): Error? { return null; }` — a `NullValue` plus a `Return`.
- `stack_trace(): StackTrace { return StackTrace(); }` — reuses the same constructor-less `Alloc` that `fase-4b` (D4) already uses to build `StackTrace`.

This pattern lives alongside the `UNREACHABLE_ABSTRACT_METHOD` dummy `lower()` already synthesizes by hand today (same place, same level of "IR function built directly, with no AST in between") — it is not a new technique in the codebase, it is the same one that already exists, applied to four real bodies instead of one unreachable one.

**D9 (this number is reused only for local reference convenience within this document — unrelated to `fase-4a`'s function-types D9) — the four classes are registered as *concrete*, with their own `ObjectLayout`/method table, not via D4's abstract `native_exceptions` path.** `Checker::register_native_exception_hierarchy` gains four more registrations, each producing a real class with `base: None`, `implements: [RuntimeError]`, fields and methods populated exactly as if a user had written it — so virtual dispatch through a `Throwable`/`RuntimeError`-typed reference works exactly as it does for any user class that implements `RuntimeError` today (mechanism already proven by D4, unchanged here).

**D10 — the four checks move to `zirk-ir/src/lower.rs`, building the exception and dispatching via `lower_pending_exception_dispatch` before emitting the real operation, reusing D1–D3 unmodified.** Concretely:
- **Division by zero** (`BinaryOp::Div`/`Mod` on integers): before emitting the division, compares the divisor with zero; if zero, builds `DivisionByZeroError("division by zero")`, throws it, runs the dispatch — the same way `lower_throw` does.
- **Invalid shift** (`Shl`/`Shr`): before emitting the shift, the same range comparison that lives today in `checked_shift` (negative or `>= bits`), but as an IR `Branch` instead of an LLVM `trap_if`.
- **Invalid repeat** (`String` repetition): the check lives today inside `zirk-runtime/src/string.rs` (`zirk_rt_invalid_repeat`), not in codegen — the count check (negative) moves to `zirk-ir`, before the call to the runtime function that keeps doing the actual repetition (the runtime stops rejecting the count, it only repeats).
- **`NaN`** (result of `Float` arithmetic): the check compares the result with itself (`x != x`) *after* the operation — unlike the other three, this checks the result, not an operand, so the floating-point operation is emitted first, and the check/throw comes after, before the result is used in any following instruction.

In all four cases, codegen no longer has the check — `checked_division`/`checked_shift`/`check_not_nan` in `emit.rs` simplify to just emitting the operation (no longer need `trap_if`), and `zirk_rt_invalid_repeat` is no longer called from `zirk-runtime/src/string.rs` for the negative-count case (the runtime keeps existing for other `str_repeat` invariants, if any — to be reviewed during implementation).

**D11 (D6 of the `fase-4b` document, renumbered here) — `lower_throws_check` runs after every call, not only `throws`-declared ones.** Before this change, the pending-slot check after a call was wired only when the callee's `throws` was non-empty. With the four native failures now throwing `zirk_rt_throw` from inside a function that may declare no `throws` at all (an implicit failure's `throws` is not declared, by language design), the caller has to check the pending slot after *any* call to remain sound — accepting the uniform cost (one more check plus a branch per call site) that D6's own original text already anticipated and accepted as the correct trade-off.

## Risks / Trade-offs

- **Uniform execution cost (D11):** every call in any compiled program pays one `zirk_rt_has_pending_exception` plus a branch, not only those declaring `throws`. Accepted — it is exactly the trade-off `fase-4b`'s own D6 already identified and recommended taking if this change were made.
- **Hand-built IR bodies (D8) do not go through the checker** — if one has a type error (for instance, a `LoadField` with the wrong index), the error only surfaces as a panic during lowering or a failure of `zirk_ir::verify`, not as a user diagnostic. Accepted because `UNREACHABLE_ABSTRACT_METHOD`'s own code already sets this precedent, and the volume is minimal (sixteen trivial bodies total, four per class).
- **Duplication of message literals**: the text that lives today in `zirk-runtime/src/failure.rs` (`"division by zero"`, etc.) is also needed as the exception's `reason` — centralized as constants shared between `zirk-ir` (which uses them as `message()`'s value) and whatever remains of `zirk-runtime`/`fatalError` (which keeps using them if the exception escapes uncaught, for `zirk_rt_uncaught_exception`'s final message), rather than kept separately.

## Migration Plan

Additive over a pipeline that already compiles and runs. Nothing existing changes behavior except D11's per-call cost (not observable except in benchmarks) and the new possibility of catching these four failures (previously impossible, now possible — a program that never uses `try`/`catch` for them still aborts exactly the same). Rollback: revert the merge; nothing depends on this yet.

## Open Questions

- None outstanding for this change's scope — confirmed before starting implementation, following the same pattern as `fase-4a`/`fase-4b`.
- Open for a future pass: `OverflowError` (needs the multi-result IR instruction question resolved) and `InvalidCastError` (not investigated in this pass) — see `proposal.md`, "Explicitly out of scope".

## Decisions — revised after implementation

What is written above (D8–D11) holds in broad outline; what follows documents where the actual implementation differed, or had to solve a problem the original text did not anticipate.

**D8 — the correct count is sixteen bodies, not twenty, because `construct` is never synthesized as a real IR function.** The original text already hinted at this by listing "sixteen... four per class" in Risks, in tension with listing five members (`construct`, `message`, `code`, `cause`, `stack_trace`) in the D8 section itself. Resolved in favor of the Risks count: `construct(reason: String)` has no function symbol of its own — `Lowering::lower_construction` intercepts it with a special case (`Alloc` + direct `StoreField` of the argument), exactly the same gap already used for `StackTrace()` (which also does not call a real constructor). A program that writes `DivisionByZeroError("message")` by hand still compiles and works — the special case covers both compiler-built construction (`Lowering::build_native_failure`, to throw the exception from a failed check) and user-written construction, with the same code.

**Task 1.3 — none of the four classes has explicit rejection of user construction.** `class Foo implements RuntimeError { construct(reason: String) {...} }` was already constructible by a user before this change; the four native classes are, deliberately, "concrete and instantiable" (`proposal.md`), so they are treated the same way — `DivisionByZeroError("message")` type-checks and compiles (test `valid_native_failure_class_is_constructible_like_any_other_runtime_error` in `zirk-sema/tests/typing.rs`). Adding a special rejection would have been more code for less consistency, with neither the proposal nor the spec delta asking for it.

**D10 — each check had to solve two block-crossing problems the original text did not mention:**
1. *Operands already lowered before the check do not survive the branch the check itself introduces* (ADR-007: a value never crosses a block). `checked_int_division`/`checked_shift`/`checked_repeat` now spill (`Lowering::spill`) their operands to a slot *before* comparing, and reload them in the continuation block before emitting the real operation — the check and the operation became a single function each (`checked_int_division`, `checked_shift`, `checked_repeat`), not "separate check, then `emit` of the operation" as the first draft suggested.
2. *`ConstInt` only declares `Int32`* (the verifier requires this — see `default_value`'s own comment, which turned out to describe a path never actually exercised in practice): a `0` or a bit width for an `Int64`/`Int8`/etc. needs `ConstInt(0)` at `Int32` followed by an `IntCast` to the real width, not `ConstInt(0)` declared directly at the target width — hence the new `Lowering::const_int_at` helper.

**D10, `NaN` — `x != x` does not detect `NaN` under the `!=` semantics the language already has.** `emit_float_binary`'s own table maps `BinaryOp::NotEq` on `Float` to LLVM's *ordered* `ONE` comparison (false for any `NaN` operand, just like `OEQ`), not the *unordered* `UNE`/`UNO` that `check_not_nan` used directly at the codegen level. `guard_nan` instead builds `!(x == x)` (`BinaryOp::Eq`, which does map to `OEQ`, negated with `UnaryOp::Not`) — mathematically equivalent to the IEEE 754 property needed, and expressible with operators the IR already has, without adding a new `BinaryOp` just for this.

**D11 — the only extra line needed was removing `if self.call_throws(call).is_empty() { return result; }` from `lower_throws_check`** (and, with it, the entire `call_throws` function, which was left with no other caller) — every other site already went through that function unconditionally. But making it unconditional exposed three pre-existing gaps that `fase-4b`'s own D1–D3 mechanism had never exercised, because before D11 almost no call inside a `finally`/`return` reached them:
1. **Infinite recursion during lowering.** `lower_pending_exception_dispatch` cloned `try_stack` to iterate over it, but never emptied the *real* `try_stack` while lowering a frame's own `finally` — a call inside that `finally` (for instance, `Resource<E>`'s `close()`, synthesized by `Self::resource_close_block`) now also triggers `lower_throws_check`/`lower_pending_exception_dispatch`, which saw the same frame still active and lowered the same `finally` again, without bound — found with `resources_match_with_closes_on_thrown_exception.zrk`, which ended in a *stack overflow* of the generated binary (the recursion, although infinite at the lowering level, did terminate at compile time thanks to how LLVM/codegen handle already-terminated blocks, so the failure only showed up at runtime). Fixed by truncating `self.try_stack` to only the frames outside the one being unwound, while lowering its own `finally` — consistent with real exception semantics (a `finally` runs in the context of what encloses it, not enclosed by its own `try`).
2. **`return expr;` did not survive its own `run_finally_through`.** The return value was lowered *before* lowering the `finally`s of the `try`s the `return` passes through; if any of those `finally`s now opens blocks (any call does, with D11), the value ended up used in a different block from the one that defined it. Fixed by spilling the value to a slot before `run_finally_through` and reloading it afterward, the same as already done elsewhere in the same file.
3. **`lower_throws_check`'s own `Void` shortcut reused an operand from another block.** When the call's return type is `Void`, the function did not spill anything to a slot (there is nothing to spill) and simply returned the original operand — valid before D11 because nothing normally *uses* a `Void` value, but `Result.Ok(someVoidCall())` does package it into a `BuildEnum`, and that use now crossed the block `lower_throws_check`'s own branch introduces. Fixed by emitting a fresh `InstKind::Undefined` in the continuation block instead of reusing the previous operand — just as information-free as the original, but valid in the correct block.

None of these three is specific to the four native failures: they are general gaps in `fase-4b`'s D1–D3 mechanism, which D11 was the first to exercise enough to find them. The tests that caught them were already in the corpus (`resources_match_with_closes_on_thrown_exception.zrk`) or derive directly from it (`FakeFile::close`'s own `return Result.Ok(this.nothing())`).

**"Duplication of message literals" risk — not centralized as constants shared between crates.** The original text proposed sharing the literals (`"division by zero"`, etc.) between `zirk-ir` and `zirk-runtime`. In practice, `zirk-ir` does not gain (nor need to gain) a dependency on `zirk-runtime` — they are independent `&str` literals on each side (the new ones in `zirk-ir/src/lower.rs`, next to each `throw_native_failure`; the existing ones in `zirk-runtime/src/failure.rs`, unchanged). Introducing a shared crate just for four text strings would have been a new architectural layer for minimal savings — the same kind of decision D8 already made (in the other direction) when rejecting the "prelude" approach to avoid gaining a bigger layering dependency than this piece warrants.

**Task 5.2 — no corpus fixture for the uncaught case.** The `crates/zirk-cli/tests/corpus/valid/` harness requires exit code `0` (`the_valid_corpus_compiles_and_produces_the_expected_output`), so a program whose failure escapes uncaught cannot live there. Verified manually, the same way `never_and_fatal_error.zrk` already documents doing for `fatalError` ("verified manually with a real program: exit code 70") — the four failures, uncaught, still abort with exit code `70`, with the message `"fatal error: an exception escaped \`main\` uncaught"` instead of each one's specific message (the abort mechanism went from `zirk_rt_division_by_zero`/`zirk_rt_invalid_shift`/`zirk_rt_float_nan` — which `codegen` no longer calls, only remaining declared with their `noreturn` attribute — to the generic `zirk_rt_uncaught_exception` `fase-4b` already uses for any uncaught exception; `zirk_rt_invalid_repeat` remains the real mechanism for the other two `str_repeat` invariants, unrelated to the count).
