> **The sections are a coverage list, not an execution order.**
>
> Classes, contracts, and generics are a mutually dependent core: classes
> need generics to be useful, generics need contracts to constrain, and
> contracts need classes to be implemented. There is no order in which one
> part finishes before the others, so reading this as "finish all classes
> before starting contracts" would lead to a dead end.
>
> Implementation proceeds through **vertical slices**:
>
> 1. Create the minimal shared representations: nominal symbols, type
>    parameters, contracts, members, and relationships between types.
> 2. Parse the minimal subset of classes, interfaces, and generics.
> 3. Register the declarations and resolve references between them, even
>    though their bodies are not yet fully verified.
> 4. Complete the implementation of contracts, `from` constraints, and
>    generic members together.
> 5. Add lowering and codegen **only** after each construct is closed in
>    the parser, resolution, and checker.
> 6. Then expand toward traits, inheritance, algebraic types, casts, and
>    optimizations.
>
> Every checked box means its rule is covered end to end, not that its
> layer is finished.

> **The objects spec was updated on August 17, 2026, and several rules in
> this group changed in content.** What was already implemented was
> realigned:
>
> - Every omitted attribute gets its type's default before the constructor
>   runs, so the constructor only needs to write what has no default (a
>   class has none).
> - `super(...)` and `super.method()` exist, which retires the provisional
>   rule that a subclass initialized inherited fields.
> - Overriding an inherited method requires `override fn`.
> - `abstract class` stopped being something that is extended: it is a set
>   of requirements adopted with `implements`, with no constructor or layout.

- [x] 11.3 Lower enums with associated data: discriminant plus payload — new `IrType::Enum(u32)`, with its own `EnumLayout` table in `checked.enums`'s id space. The "payload" is not a real byte-level union: each variant gets its own field range, concatenated (not overlapping) — simpler and with no risk of reinterpreting another variant's bytes, at the cost of a layout sized for all variants at once rather than just the largest one; with this phase's typical variant count the cost is not tight. A traditional enum (no variant with data) is still plain `Int32`, with no change in representation or performance. Its own construction (`InstKind::BuildEnum`, no `Alloc`) and discriminant read (`InstKind::Discriminant`, `extractvalue` in LLVM). Found and fixed three real findings while unblocking this path, all preexisting and never reached before because constructing data-carrying variants was completely blocked: `contract_method_of` and `lower_contract_call` did not check `variant_accesses` before requesting the receiver's type (unlike `method_of`/`lower_method_call`, which did) — `EnumName.Variant(...)` as a call's callee crashed while trying to resolve "EnumName" as a variable; and `arm_value_type` requested the type of the first match arm's body before the actual loop declared that arm's bindings, so any `match` whose first arm read its own binding (`y => y`, not only the new destructuring case) crashed — this had never been noticed because no previous test wrote that exact pattern
- [x] 11.4 Lower pattern destructuring to payload reads — reuses `InstKind::LoadField` with no new instruction: every sub-pattern of a `Variant` that is a `Binding` binds to its field via `LoadField` with the flattened index that `EnumLayout.variants[discriminant]` already gives. Also gated: a generic enum with data (combines with 11.1's specialization, out of scope, same as records/value classes in 11.5). Verified with real programs: construction with reordered named arguments, `match` with bindings used in the body, wildcard discarding a field, and both gates (generic, nested literal pattern) failing cleanly without a crash
- [x] 11.5 Lower records and value classes with no indirection — new `IrType::Value(u32)` in `zirk-ir/src/ir.rs`, with its own `ValueLayout` table (fields only, no header or dispatch table) and an id shared with `ObjectLayout`/`checked.classes` (`ClassType.kind` decides which table to look at). Its own construction (`InstKind::BuildValue`, packs fields with no `Alloc`, filling in defaults for fields omitted by name); field reads reuse `LoadField` with no changes in `lower.rs` — only the LLVM backend distinguishes: `extractvalue` on the value when it is `IrType::Value`, GEP+load on the pointer when it is `IrType::Object`.   **Closure addendum (14.3):** a real, preexisting finding, never exercised before — calling a record or value class's own method directly (`p.length()`, without going through any contract) crashed: `method_of`/`lower_method_call` only recognized `IrType::Object`, so the call fell into the field-access path and `field_position` blew up because the method's name is not a field. - [x] 11.6 Lower the checked cast to a descriptor comparison — the descriptor gains a second list, besides the contracts one: the ids of the class itself and every transitive base (`ObjectLayout.ancestors`), which a checked cast looks up at runtime. `InstKind::CheckedCast` loads the object's descriptor and calls `zirk_rt_check_cast` (new, in `zirk-runtime`), which walks that list and aborts the process via `zirk_rt_invalid_cast` if the target type does not appear — there is no `try`/`catch` yet (Phase 4), so a failed cast is controlled termination, the same as any other invariant this module already guards (overflow, division by zero, missing contract). `zirk_rt_contract_table` was updated for the descriptor's new shape `[method_table | ancestor_count | ids... | contract_count | pairs...]`. Scope: the checker (`cast_is_directly_lowerable`) only lowers the identity cast (same type, any class — no check needed, the base class satisfies `Object`/`Value`/`Enum` alike) and class↔class or contract→class, both non-nullable; unions (do not lower at all yet, 8.7/11.x) and generic parameter constraints are left with their own `NOT_LOWERED`, same as any cast where either side is nullable (deciding what `null` means for the check is a separate question). Found and fixed a real finding **unrelated to casts**, exposed by the same path: `lower_expr_as` only knew how to widen `T` to `T?`; any ordinary object widening — `mut a: Animal = Dog();`, with an explicit annotation, or passing a subclass where the base is expected as an argument — lowered with the concrete value's IR type (`Object(Dog)`) instead of the expected one (`Object(Animal)`), and the verifier rejected it as invalid IR. This had never hit a test before because no program in the phase wrote that exact pattern with an explicit annotation. Fixed with `InstKind::Retype`, a type change with no runtime work (the object's address does not change, only which static type it promises). Verified with real programs: upcast/downcast between a class and its base, contract→class cast (success and failure with exit code 70), identity on a scalar, and both gates (union — pending 8.7/11.x —, nullable) failing cleanly
