## 2. Checker — real callable type

- [x] 2.1 `resolve_written_type` (or its equivalent) builds a real `Base::Function`/`FnType` from the written annotation, reusing `Checker::intern_fn_type` (structural interning, already exists) — not the non-interned path currently used by lambdas
- [x] 2.2 Contravariant compatibility on parameters / covariant on result, with matching labels/optionality/variadic, for: named function, capture-free lambda, bound/unbound method — implemented for named function and capture-free lambda (`Checker::fn_shapes_compatible`/`callable_assignable`); bound/unbound method not exercised (no real use case in this pass's corpus, the same structural path would apply)
- [x] 2.3 `expect_assignable`: a named function or capture-free lambda toward a `Fn(...) => R` position is accepted structurally (D12) — withdraw or scope the current rejection of "each closure has its own type" for this specific case, without touching the rejection between two closures with distinct captures
- [x] 2.4 D14: a closure with captures satisfies a `Fn(...) => R` position only when the literal appears directly in that position — **scoped after the actual implementation** to a local initializer (`check_let`) and a `return` expression (`check_return`), the only two cases where a single static syntactic position soundly backs the mechanism; argument at a call site and field value are NOT supported in this pass (see `design.md` addendum) — they are rejected with the same new diagnostic, not with a panic
- [x] 2.5 D14: the declared return type of a function that is a `Fn(...) => R` with captures requires that every `return` producing a `Base::Function` refer to the same literal (same span/id) — two distinct literals are rejected with a new, clear diagnostic (`E0439`), not a generic `TYPE_MISMATCH`
- [x] 2.6 D14: reassigning a `Fn(...) => R` local from a literal with captures to a different one is rejected with the same diagnostic — scoped to reassignment from a local ALREADY initialized with a literal; a `mut f: Fn(...) => R;` without initializer followed by an assignment with captures is also rejected (adoption via plain assignment is never supported, only via initializer — see `design.md` addendum)
- [x] 2.7 `invalid_closure_returned_from_a_function` and `invalid_generic_inference_from_a_closure_argument` (`crates/zirk-sema/tests/typing.rs`) become valid cases for the single-literal form (renamed `valid_closure_returned_from_a_function`/`valid_generic_inference_from_a_closure_argument`); added `invalid_two_differently_captured_closures_in_one_return_type` as the case that remains rejected
- [x] 2.8 `is` between two callable values is accepted (D15); `==`/`!=` remain rejected unchanged — test for both
- [x] 2.9 Recursive lambda with explicit binding type (`mut fact: Fn(Int32) => Int32 = (n: Int32): Int32 => ...;`) — manual test with a real program (`callable_types.zrk`); required a new mechanism not covered by D12–D15 (see `design.md` addendum): pre-declaring the binding before checking its own initializer, and in IR a direct self-call instead of a real capture. Found during review: using the recursive binding as a value (not as the direct callee) panicked in `zirk-ir` instead of being rejected in the checker — fixed with an AST walk of the body (`Checker::check_recursive_reference`) that rejects any occurrence that is not the direct callee of a `Call`, including one reached from a nested lambda (`E0440`)
