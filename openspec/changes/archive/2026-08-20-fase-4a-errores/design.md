## Context

`ZIRK_ROADMAP.md` names Phase 4 "Errors and memory" as one phase, but the two halves have almost nothing in common: the memory strategy needs a real evaluation against Zirk programs with closures and objects before it can close ([ADR-003](../../../docs/decisions/ADR-003-memoria.md)), while `Result<T,E>` is an ordinary generic algebraic enum that Phase 3's own generics work already made possible. This change is the error half only, and only the *expected*-failure quarter of that half — `Result<T,E>` — not the *extraordinary*-failure quarter (`try`/`catch`/`throw`/`Throwable`), which needs exception-propagation machinery (unwinding or an equivalent, `finally` running on every exit path) this change does not build.

The authoritative source for `Result`'s exact shape is `docs/ERROR_RESOURCE_PERMISSION_SEMANTICS.md` section 2 — marked "authorial source of truth", accepted 2026-08-16, explicitly superseding older conflicting descriptions elsewhere. It gives `Result`'s full method signatures, including four (`map`, `map_error`, `and_then`, `or_else`) that introduce a type parameter of their own beyond `Result`'s own `T`/`E`. `MethodInfo` (`zirk-sema/src/types.rs`) has no `type_params` field — only a class/contract/enum as a whole can be generic today, not one of its individual methods — so those four, plus `or_throw` (which additionally needs exceptions), are real, separate future work, not a mechanical extension of this change.

A prior pass of this same agent misdiagnosed "an enum cannot implement `to_string()`" as Phase 3 debt. It is not: `ZIRK_LANGUAGE_SPEC.md` section 7 states plainly that "enums are data-only and declare no user methods", restated independently by `ZIRK_STDLIB_SPEC.md` and the handbook's own enum pages. `docs/init/ZIRK_AGENT_PROMPT.md` is corrected. This closes off what would have been the wrong foundation for `Result`'s own API: it cannot be a table of enum methods, because that mechanism must not exist at all. It is recognized structurally instead, the same way explicit `.to_string()` on a native scalar already is (`Checker::is_native_to_string_call`, Phase 3b) — by receiver type and method name, not through a method table.

## Goals / Non-Goals

**Goals:**

- `Result<T,E>` as a compiler-known generic algebraic enum, matching `docs/ERROR_RESOURCE_PERMISSION_SEMANTICS.md` section 2's `enum Result<T, E> { Ok(T); Error(E); }`.
- The non-generic-method quarter of its API: `is_ok`, `is_error`, `ok_or_null`, `error_or_null`, `get_or`, `unwrap`, `unwrap_error` — called with ordinary dot syntax on a `Result` value. `get_or_else(factory: Fn() => T)` turned out to need a second thing this change does not build (see Decisions, D4) and moved to Non-Goals alongside the generic combinators.
- Mandatory consumption: a `Result`-typed bare statement is a compile error; `_ = expr;` is the explicit discard.
- `Base::Never`, the bottom type, and `fatalError(message: String): Never` as a compiler-recognized function.
- `unwrap`/`unwrap_error` on the wrong variant call `fatalError`, reusing the controlled-abort pattern every checked arithmetic/cast operation already has since Phase 1.

**Non-Goals:**

- `map`/`map_error`/`and_then`/`or_else`/`or_throw` — need per-method generic type parameters, a real new inference feature (see Context). Also out: any other method-level generic (this is not scoped to `Result` specifically, it just happens to be where the gap first matters).
- `get_or_else(factory: Fn() => T)` — its parameter is a function type, and `docs/init/ZIRK_AGENT_PROMPT.md` is explicit (design D9) that function types have no syntax yet in Zirk: a closure infers its type locally but cannot be annotated as a parameter, return, or field type anywhere in the language, not just for `Result`. See Decisions D4.
- `try`/`catch`/`finally`/`throw`, `Throwable`/`RuntimeError`/`Error`/`StackTrace`, `throws` in function signatures, compiler-known `RuntimeError` subclasses for existing safety checks (division by zero, overflow, invalid cast, …) — `fase-4b-excepciones`.
- `Resource<E>`, `match with` — depends on exceptions.
- The memory strategy, `unsafe`/`Pointer<T>`, safe/weak/dependent references, `inmut::strict` — the rest of roadmap Phase 4; needs ADR-003's own evaluation process, not this change.
- General enum methods — the language does not have these and must not gain them; `Result`'s API is a structural special case, not a precedent to generalize.

## Decisions

**D1 — `expected_type`, a single-shot field on `Checker`, seeds generic-parameter inference from the surrounding context.** `infer_type_params` could only ever solve a type parameter from an argument; `Result.Ok(5)` used where a `Result<Int32, String>` is expected has no argument that names `E` at all. Rather than thread an `expected: Option<Type>` parameter through the whole `check_expr` call graph, `Checker` gained one field, cleared unconditionally at the top of `check_expr` (`let expected = self.expected_type.take();`) so a nested call never inherits a stale value — only `check_let` (from an explicit annotation) and `check_return` (from `current_return`) set it, immediately before the one `check_expr` call it is meant for. `check_call` threads it down to `check_variant_construction`, which turns it into a `seed: HashMap<u32, Type>` for `infer_type_params` when the expected type is a matching `Base::EnumInstance` — an argument that disagrees with the seed still conflicts normally, since seeding happens before the argument loop runs.

**D2 — `Base::Never` is accepted everywhere and contributes nothing at a `unify` join, mirroring but not reusing the `null` rules.** `Type::accepts` returns `true` for a `Never` operand before the `null` check runs (unconditional, not "wherever absence is admitted" the way `null` is); `Type::unify` returns *the other side* for a `Never` operand, not a nullable widening of it — `cond ? 5 : fatalError(...)` types as `Int32`, never `Int32?`. The same asymmetry repeats through IR lowering: `lower_ternary`/`lower_if_expr` skip `Store`+`Jump` for whichever branch's type is `Never` and terminate it with `Terminator::Unreachable` instead, and `lower_expr_as` falls back to `default_value(expected, span)` as a type-correct placeholder when asked to store a `Never`-typed initializer (scoped to `Call | If | Ternary` expression kinds only, after two corpus regressions — `Lambda | Null | Range` and `Match` — showed `type_of` cannot safely be probed that early for those).

**D3 — `Result<T,E>` is a real registered `enum`, not a hand-rolled type; its method API is recognized structurally, never through a method table.** `register_native_result_enum` injects `Result` into `self.enums` the same "build the tables directly, no parsing" way `register_native_iteration_contracts` already does for `Iterable`/`Iterator`/`Iteration<T>` — which is what makes generic-enum instantiation, pattern matching, and exhaustiveness checking work for it for free once those were made instance-aware (see the bug list below). `EnumType` has no `methods` field on purpose (`ZIRK_LANGUAGE_SPEC.md` section 7: enums are data-only), so `is_ok`/`unwrap`/… are dispatched by receiver type and name in `check_call` (`Checker::check_result_method_call`) and again independently in `zirk-ir/lower.rs` (`Lowering::result_method`/`lower_result_method_call`) — the same structural-dispatch shape `to_string()` on a native scalar already established in Phase 3b, not a new pattern. Each recognized name builds a throwaway `Signature` and hands it to the ordinary `check_direct_call` machinery, reusing its arity/naming/type diagnostics rather than duplicating them by hand for eight names.

**D4 — `get_or_else` moved out of scope after implementation exposed a real conflict with design D9, not a workaround.** Its signature (`factory: Fn() => T`) needs a closure-typed parameter, and D9 (`docs/init/ZIRK_AGENT_PROMPT.md`) is explicit that function types have no syntax yet anywhere in Zirk — not a `Result`-specific gap. Fabricating a `Base::Function` id around that restriction (which `expect_assignable` would then reject anyway: two closures of the same shape still compare unequal by id, "a closure cannot be replaced by another one") would have been exactly the shortcut D9 left for a future phase to close properly. `proposal.md`'s scope was corrected to move it beside the generic combinators rather than ship a special case.

**D5 — four bugs surfaced, in sequence, from `Result` being the first *two*-argument generic enum and the first one a user program actually pattern-matches against; each is now fixed at its source rather than special-cased for `Result`.** In order of discovery: (A) `expect_pattern_type` didn't consult `bare_enum_matches_instance`, so `Result.Ok(value)` never matched a `Result<Int32,String>` scrutinee — fixed by adding that call, the same helper construction/return contexts already used. (B) `check_variant_pattern` read the *template* enum's unsubstituted field types, so a destructured binding came out typed as bare `Base::Param` instead of `Int32` — fixed by substituting `associated` through a map built from the scrutinee's own `Base::EnumInstance` args. (C) `check_exhaustive` only recognized a bare `Base::Enum` scrutinee, so a `Result<T,E>`-typed `match` could never be judged exhaustive — fixed by also resolving the enum id from `Base::EnumInstance` before the coverage check. (D) at IR lowering, both `lower_match`'s inline destructuring code and the sibling `declare_pattern_types` indexed `self.module.enums[...]` using the *template* id from `enum_id_of()` — but a generic enum's template-level `EnumLayout` is an empty placeholder (only the specialized copy, reachable through the scrutinee's own `IrType::Enum(module_id)`, has real field/variant data) — fixed by splitting each site into a `template_id` (kept only for the discriminant lookup against `self.checked.enums`) and a `module_id` derived from the scrutinee's own IR type. A fifth, related bug (E) surfaced in `resolve_written_type`: a *written* type annotation like `Result<Int32, String>` resolved to a bare `Base::Enum(template_id)` — the enum branch never consulted `reference.arguments` at all, unlike the class branch right next to it — so `mut r: Result<Int32, String> = …;` silently declared `r`'s slot with the empty template layout. Fixed by mirroring the class branch: intern against `checked.enum_instances` and return `Base::EnumInstance` when arguments are present. None of (A)–(E) are `Result`-specific; each was a latent gap in the two-argument/first-real-user-match path that any future generic enum would have hit identically.

**D6 — the seven in-scope methods' block-opening lowering (`ok_or_null`, `error_or_null`, `get_or`, `unwrap`, `unwrap_error`) required teaching `opens_blocks` about a call that branches without any of its arguments doing so.** Every existing use of `opens_blocks` assumed a `Call` only opens blocks through its arguments (`e.args.iter().any(opens_blocks)`) — true for an ordinary function call or `to_string()`, false for `result.get_or(1) ?? 2`, whose *left* operand itself lowers to a branch. Converting the free function into a `Lowering` method (needed so it can consult `self.result_method(call)`) surfaced this directly: without the fix, `lower_and_hold`'s `will_branch` came out `false` for a `Result` method call, and the coalesce/binary/interpolation code that follows read its operand's value across a block boundary the IR forbids (ADR-007) — caught immediately by `verify.rs`'s "values do not cross blocks" check rather than a silent miscompile.

**D7 — `unwrap`/`unwrap_error`'s abort message is a static string, not the "found variant, safe value representation" the spec describes.** Building a text form of the payload would need it to be `is_printable` — not guaranteed for an arbitrary `T`/`E` — and no compiler-generated failure has source-location plumbing yet (`zirk_rt_overflow` and its Phase 1 siblings have the identical gap). Closing that uniformly is a separate, general piece of runtime-diagnostics work, not something to build once, narrowly, for `Result` alone; the message still names which variant was wrong and what to do instead.

**D8 — mandatory consumption is scoped to a bare `Stmt::Expr` whose type is a `Result` instance, not a general `#[must_use]` mechanism.** `_ = expr;` is the escape hatch: `check_assign` special-cases an assignment target literally named `_` to check the value and return without resolving a binding — so it is a `Stmt::Assign`, never reaching `Stmt::Expr`'s own check at all, matching the doc example (`docs/handbook/02-handbook/15-errors/02-handling-result.md`) exactly. `IrType`/lowering needed the matching half: `lower_assign` special-cases the same target name to lower the value for its side effects and discard it, since no slot named `_` was ever declared to store into.

**D9 — Un intento posterior de destrabar `map`/`map_error`/`and_then`/`or_else` confirmó el bloqueo de D4, con una razón más profunda que la comparación nominal de `expect_assignable`.** La hipótesis a probar era si un despacho estructural podía construir la verificación en Rust sin que el usuario escribiera `Fn(T) => U` en ningún lado, evitando así el camino que D4 ya había descartado (fabricar un `Base::Function` y pasarlo por `check_direct_call`/`expect_assignable`). Existe un segundo camino, real, que sí evita esa comparación: `check_call` ya *invoca* una closure leyendo su `FnType` propio directamente de `self.fn_types[id]` (checker.rs, ~línea 7053) en vez de comparar dos `Base::Function` entre sí — así es como `f(5)` tipa una llamada directa a una closure hoy. En teoría, `map` podría leer el `fn_type.returns` de la lambda ya tipada por `check_expr` y usarlo como `U` sin pasar nunca por `expect_assignable(Function, Function)`.

Ese camino choca con una segunda barrera, independiente de `expect_assignable` y ya presente en el código antes de esta investigación: `infer_type_params` (checker.rs, ~línea 7327) rechaza explícitamente resolver un parámetro de tipo genérico a partir de un argumento `Base::Function`, con un diagnóstico que cita D9 por nombre — *"a closure may not be annotated as a parameter, return or field type, and a generic argument is no exception"*. Leer `U` desde el `fn_type.returns` de la lambda para instanciar `Result<U,E>` es exactamente eso: inferir un parámetro de tipo nuevo (el `U` propio del método) a partir de una closure, solo que con el árbol de llamada reacomodado para no pasar por `expect_assignable`. El guardia no es un efecto colateral de cómo se comparan dos `Base::Function`; es una regla deliberada, ya escrita, que trata cualquier inferencia de tipo genérico desde una closure como la anotación `Fn(T) => U` "bajo otro nombre" — el mismo lenguaje que ya usa el comentario en esa línea del código.

En consecuencia, los cuatro combinadores (`map`, `map_error`, `and_then`, `or_else`) permanecen fuera de alcance por la misma razón que `get_or_else`: D9 sigue sin resolverse, y ningún camino de despacho estructural disponible hoy —ni el de D4 ni el explorado aquí— lo evita. Cerrarlos de verdad necesita que una fase futura implemente la sintaxis `Fn(P...) => R` que D9 ya dejó decidida en su semántica (`fase-3-objects-and-type-system/design.md`, D9), momento en el que `MethodInfo` también necesitará su propio `type_params` (ver nota de alcance en `proposal.md`). No se escribió código de producción para esta investigación: implementarlo ahora habría exigido debilitar el guardia de `infer_type_params` específicamente para este caso, reabriendo el hueco que esa regla existe para cerrar.

## Risks / Trade-offs

- **`Result<T,E>` is two type parameters where `Iteration<T>` (the only existing compiler-known generic enum) has one.** If the existing generic-enum-instantiation machinery assumes single-arity anywhere non-obvious, this is where it would surface. Audited as the first implementation task, before committing to the rest of the shape — mirrors how the Phase 3b integer-widths migration started with an audit before writing any new width.
- **Structural method dispatch by name (`is_ok`, `unwrap`, …) risks colliding with a real method a user's own class happens to declare with the same name.** Scoped narrowly: the dispatch only fires when the receiver's type is specifically the compiler-known `Result` enum instantiation, never for a class/contract/value-class receiver — exactly the same scoping `is_native_to_string_call` already uses for `to_string()`.
- **Mandatory consumption is a new category of check** — nothing today rejects a bare discarded expression statement of any type. Scoped to `Result` specifically (not a general `#[must_use]`-style annotation mechanism), since that is all the spec asks for; a general mechanism is not built speculatively ahead of a second type that would need it.

## Migration Plan

Additive over a pipeline that already compiles and runs end to end. Nothing existing changes behavior; `Result`, `Never`, `fatalError` and mandatory discard are all new surface. Rollback: revert the merge, nothing later depends on this yet.

## Open Questions

- **Exact wording of the mandatory-discard diagnostic and which statement shapes count as "used".** `docs/handbook/02-handbook/15-errors/02-handling-result.md` shows a bare call statement (`load(path);`) as the rejected shape and `_ = load(path);` as accepted — an assignment, a `return`, or an argument position all clearly count as "used"; resolved during implementation against those examples, not a genuine open design fork.
