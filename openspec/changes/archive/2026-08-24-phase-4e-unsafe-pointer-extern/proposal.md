## Why

Phase 4e's `unsafe {}`/`Pointer<T>`/`commit {}` surface is, per today's exploration (`docs/decisions/ADR-003-investigacion-fase-4.md`), the one large Phase 4e piece that does not depend on ADR-003's still-open memory-strategy decision — but it has zero grammar surface today: `unsafe` is rejected purely by lexer phase-gating (`E0302`), `Pointer<T>` by the same mechanism (`E0402`), and `commit`/`extern` do not exist as keywords at all. Worse, calling a native function — item 2 of `MEMORY_AND_UNSAFE_SEMANTICS.md` §9's own closed unsafe operation set — has no declared Zirk-side syntax anywhere in the normative documents; `ZIRK_LANGUAGE_SPEC.md` only says native interoperability "uses the C ABI as its stable boundary", never how a Zirk program declares a native function. `docs/decisions/ADR-015-declaracion-extern.md` (this session) closes that specific gap with a scoped decision: a single-item `extern "C" fn name(...): T;` declaration, a narrow ABI-safe type surface, and no new library-linking manifest (deferred to Phase 6).

This change delivers the smallest coherent slice that makes `unsafe {}` genuinely useful without waiting on ADR-003 or Phase 6: raw pointer construction/read/write/arithmetic/cast over Zirk's own managed locals, `commit {}` as the syntactic irreversible-effect boundary, and `extern "C" fn` calls through it — deliberately excluding `NativeSlice<T>`/volatile access/native-union access/weak atomics, each either dependent on more machinery (bounds-checked views) or currently vacuous (no union or `Atomic<T>` type exists to protect).

**Implementation note (added after the fact, not part of the original plan):** design.md's own "Risks/Trade-offs" anticipated this slice might not fit one pass and pre-authorized splitting D1-D4/D7-D8 (pointer core, `extern`) from D5-D6 (the transactional journal/rollback). That split happened: this change delivers D1-D4/D7-D8 only. `unsafe {}`/`commit {}` parse and are context-checked correctly, but neither block journals writes or rolls anything back on failure yet — see "Explicitly out of scope" below and `tasks.md` sections 8/10 for the exact cut line. The journal is real remaining Phase 4e work, not abandoned.

## What Changes

- New keywords/grammar: `unsafe fn` (function modifier), `unsafe { }` (block), `commit { }` (block, valid only nested inside `unsafe`), `extern "C" fn name(params): ReturnType;` (top-level declaration, no body, per ADR-015).
- New type: `Pointer<T>`, with `T` restricted to `Void` (return-only), `Boolean`, `Int8`..`Int64`, `UInt8`..`UInt64`, `Float32`/`Float64`, or another `Pointer<U>` — the ABI-stable subset ADR-015 defines. `Byte` becomes a recognized alias for `UInt8` (matching `MEMORY_AND_UNSAFE_SEMANTICS.md`'s own `Pointer<Byte>` examples, which assumed a type this change is the first to actually define).
- `Pointer<T>` operations: `Pointer.from(place)` (address of an addressable local/field), `.is_null`, `.read()`, `.write(value)`, `.offset(n)`, `.offset_bytes(n)`, `.cast<U>()` — each requiring an enclosing `unsafe {}`.
- The checker tracks unsafe/commit context (a stack, like existing `loop_depth`/`in_constructor`) and rejects: any of the above pointer operations outside `unsafe`; a `Pointer<T>` value returned, stored in a field, or captured by a closure (conservative, sound escape rule — no per-value provenance tracking yet, matching the spirit of the existing "Native view escapes its borrow" rule this change extends to `Pointer<T>`); `commit {}` outside `unsafe`; calling an `extern "C" fn` outside `unsafe` and `commit` together (every extern call is treated as potentially irreversible, per ADR-015 — no purity inference).
- `extern "C" fn` declarations resolve against whatever the system linker already provides (libc, `zirk-runtime`'s own transitive links) — no new native-library-linking manifest mechanism (ADR-015; that integration is Phase 6).

### Explicitly out of scope

- **The transactional journal itself (design D5/D6): `unsafe {}` does not yet record writes and does not roll anything back on a controlled `Error`/exception/trap, and `commit {}` does not yet durably publish anything — both lower as ordinary blocks today.** The checker's context rules (unsafe/commit required, in the right nesting) are fully enforced regardless, so no unsound program is accepted — a program that *relies on* rollback behaving correctly is simply not yet distinguishable, at runtime, from one that doesn't. This is the one item in this list that is genuinely still-pending Phase 4e work, not a deliberate never-do; a follow-up change builds `crates/zirk-runtime`'s journal module and the corresponding IR lowering (design D5/D6 are unchanged and ready to implement against).
- `NativeSlice<T>`/`NativeSliceMut<T>` validated views, `.read_volatile()`/`.write_volatile()`, and `pointer.as_slice_mut(length)` — each needs bounds-checked view codegen this change does not build; left for a follow-up once the pointer core above is verified.
- Untagged native-union member access — no union type exists anywhere in Zirk; nothing to gate.
- Weak atomic ordering — `Atomic<T>` is Phase 5; nothing to gate.
- The isolation restrictions in `MEMORY_AND_UNSAFE_SEMANTICS.md` §11 about `await`/task/thread inside a reversible transaction — `task`/`thread`/`await` are Phase 5; there is nothing yet for these restrictions to reject, so no checker rule is added for them (adding one now would be dead code guarding against constructs that cannot be written).
- A native-library-linking manifest (`requires`/`during: build` extended to native symbols) — ADR-015's own explicit deferral to Phase 6.
- Permission-gating an `extern`/`commit` call — permissions are not a runtime concept yet (already noted in `fase-4d-callables`); ADR-015 defers this to whenever Phase 6 builds the real permission system.
- Automatic bounded native pinning of a *movable* managed object — vacuous today: the runtime never moves anything (ADR-003 still open), so "pinning" has no live object-movement to guard against yet. `Pointer.from(place)`'s escape rule (this change) is the load-bearing safety mechanism until a mover exists.

## Capabilities

### New Capabilities
(none — extends `zirk-memory-safety`, `zirk-grammar`, `zirk-type-system`, `zirk-native-codegen`, each already scoped to this material)

### Modified Capabilities
- `zirk-grammar`: its existing "Safety and concurrency grammar" and "Contextual safety restrictions" requirements already mandate parsing `unsafe fn`/`unsafe {}`/`commit {}` and diagnosing unsafe-only operations outside their boundary — reaffirmed verbatim, delivered by this change. `extern "C" fn` declaration syntax has no prior requirement anywhere in this spec (confirmed by search before writing this proposal) and is genuinely new — added as its own requirement, per `docs/decisions/ADR-015-declaracion-extern.md`.
- `zirk-type-system`: its existing "Memory and task type family" requirement already mandates `Pointer<T>` exist as a type — reaffirmed verbatim for the subset this change delivers (`NativeSlice<T>`/`NativeSliceMut<T>` remain undelivered, out of scope here). `extern "C" fn`'s ABI-safe signature typing has no prior requirement and is added as its own requirement (ADR-015).
- `zirk-memory-safety`: its existing "Closed unsafe operation set" and "Pointer and native-view behavior" (the pointer-specific half; native-view behavior stays undelivered) requirements are reaffirmed verbatim, delivered for this change's scoped subset. "Irreversible commit boundary" is reaffirmed verbatim but only its syntactic/context half is delivered here (commit required around an irreversible effect); "Transactional unsafe mutation" (the journal/rollback contract itself) is reaffirmed verbatim as still-normative but **not delivered by this change** — see "Explicitly out of scope".
- `zirk-native-codegen`: no prior requirement covers declaring/linking an external native symbol — added as its own requirement (ADR-015's linkage decision: resolve against whatever the system linker already provides, no new manifest).

## Impact

- Affected code: `crates/zirk-lexer` (keywords), `crates/zirk-ast` (new statement/item/type nodes), `crates/zirk-parser` (grammar), `crates/zirk-sema` (context tracking, `Pointer<T>` typing, escape rule, `extern` signature validation), `crates/zirk-ir` (new `Pointer` IR type, pointer instructions, `extern` declarations), `crates/zirk-codegen-llvm` (pointer ops as LLVM `ptr` load/store/GEP, `extern` symbol declarations). `crates/zirk-runtime` is **not** touched by this change — the journal module is follow-up work (see "Explicitly out of scope").
- `docs/decisions/ADR-015-declaracion-extern.md` (this session, already written) is the syntax/scope decision this change implements.
- Public documentation: `docs/init/ZIRK_ROADMAP.md` Phase 4e bullet "Implement `unsafe {}`, `Pointer<T>`, native slices, and compiler-enforced memory-safety boundaries" gets a status note (partial — pointer core and `extern`, not native slices); `docs/handbook/13-appendices/07-current-limitations.md` gets its `unsafe`/`Pointer<T>` line updated. `../zirk-lang-site` sync required per project convention once these land.
- No breaking changes: `unsafe`/`Pointer`/`commit`/`extern` are currently rejected keywords/types; nothing that compiles today changes behavior.
