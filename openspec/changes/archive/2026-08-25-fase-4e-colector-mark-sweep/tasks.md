## 1. IR — header layout and root descriptors

- [x] 1.1 Grow the object header representation in `crates/zirk-ir` (`ObjectLayout`, wherever the header's word count is fixed) from one word (dispatch descriptor) to three: descriptor (unchanged), `next` (intrusive allocation-list pointer, mark bit in its low bit), `size` (allocation byte size). Confirm no existing header-offset computation for the *fields following it* changes — the header grows, field offsets after it shift by the same fixed amount for every object uniformly, which is exactly what `ADR-012` already anticipated.
  - Design note: `zirk-ir` itself never hardcoded the header's word count as a literal — that number (`OBJECT_HEADER_FIELDS`) lives entirely in `crates/zirk-codegen-llvm/src/emit.rs`, the only place that lays out the actual LLVM struct. So this task's real change is there (`OBJECT_HEADER_FIELDS: u32 = 1 -> 3`, `object_struct` gains `next`/`size` fields between the descriptor and the class's own fields); `zirk-ir`'s `ObjectLayout` doc comment was updated to describe the new three-word shape so a reader doesn't have to cross-reference codegen to know it changed. `field_pointer`'s existing `index + OBJECT_HEADER_FIELDS` arithmetic needed no other change — every field after the header shifts by the same fixed amount uniformly, exactly as anticipated.
- [x] 1.2 Implement design D4: identify every IR instruction whose result type is a managed reference (`Object`, a `Closure` capturing one, or a `Value`/`Enum` containing one — walk the layout the same way existing reachability-adjacent code does, e.g. wherever deep-clone-adjacent or field-write checks already recurse through a `Value`/`Enum`'s own layout) and spill its result to a synthetic slot immediately after the instruction that produces it, before the value is used in any expression that can reach an allocation.
  - Implemented as `IrType::is_managed_reference(&Module) -> bool` (`crates/zirk-ir/src/ir.rs`) plus an unconditional spill inside `FunctionLowering::emit` itself (`crates/zirk-ir/src/lower.rs`), not at individual call sites — every value-producing instruction goes through that one function, so this closes the hazard for every current and future instruction kind uniformly, including a plain `Load` of an already-named local (its own slot can be overwritten before the next collection point, so the *value in hand* must be re-spilled, not just its origin slot). Reuses the exact `declare_slot` + `Store`-effect shape `lower_throws_check` already established.
- [x] 1.3 Compute a static per-function root descriptor (design D2): the set of slot offsets, across both named `Slot`s and D1.2's synthetic ones, whose type is a managed reference. Attach it to `Function` (or wherever per-function metadata already lives) so codegen can emit it as static data.
  - `Function.gc_roots: Vec<SlotId>`, computed once per function by `gc_roots_of` right before each `Function` literal is built (all ~9 construction sites in `lower.rs`, including the four hand-built native-failure method bodies and lambda lifting). Codegen (task 2.3) turns each root slot into one or more actual root *addresses* — see that task's own note on why "offset" ended up meaning "GEP index path", not a byte offset, for this specific descriptor.
- [x] 1.4 IR-level tests: a function with mixed reference/scalar locals produces a root descriptor naming exactly the reference-typed ones; a multi-argument call with two managed-reference-typed constructor arguments produces synthetic slots for both (design D4's own motivating case), in evaluation order.
  - `crates/zirk-ir/tests/lowering.rs`: `gc_roots_names_exactly_the_reference_typed_slots`, `multi_argument_constructor_calls_spill_each_argument_before_the_next_is_built`. Both pass.

## 2. Codegen (zirk-codegen-llvm)

- [x] 2.1 Emit the grown header (task 1.1) at every object-construction site — descriptor unchanged, `next`/mark/`size` initialized to a sentinel the runtime's own allocation path (task 4) fills in properly (or have `zirk_rt_alloc` itself own initializing these fields, whichever keeps the header's shape a single source of truth — design D1 leaves this open, decide by matching how the descriptor word itself is already set today, constructor-site or allocator-site).
  - Resolved the open question: **allocator-site**, matching that `size` is already a runtime parameter `zirk_rt_alloc` receives at every call — it is the single source of truth for both the allocation itself and the header word that records it, the same way `Alloc`'s own codegen is the single source of truth for the descriptor word. `crates/zirk-codegen-llvm`'s `Alloc` case is otherwise unchanged (still only stores the descriptor into word 0); `crates/zirk-runtime/src/collector.rs::register` initializes `next`/`size` right after the underlying allocation succeeds, before `zirk_rt_alloc` returns.
- [x] 2.2 Zero-initialize every reference-typed slot (named and D1.2's synthetic ones) immediately after its `alloca`, before any other codegen for the function (design D5).
- [x] 2.3 Emit `zirk_rt_push_frame(descriptor, frame_base)` once at function entry, after task 2.2's zero-init. The static descriptor from task 1.3 becomes a codegen-emitted constant/global per function.
  - Design deviation, documented here as instructed (tasks.md 2.1's own allowance for resolving a genuine ambiguity): this codebase's `FunctionEmitter` gives every `Slot` its own individual LLVM `alloca` (confirmed by reading `emit.rs` before designing this), not one combined per-function frame struct — so there is no single `frame_base` pointer for a "`frame_base + offset`" scheme to add byte offsets to. Implemented instead as: at function entry, codegen walks each `gc_roots` slot's own type (`gc_reference_paths_of`, recursing through `Value`/`Enum`/`Closure`/`Nullable` field indices) and, with real `build_struct_gep` instructions (`FunctionEmitter::apply_gc_path`), computes the actual address of every managed-reference field it contains — for a plain `Object`-typed slot this is just the slot's own alloca'd address. Those addresses are stored into a small stack-allocated array, and `zirk_rt_push_frame(roots_array_ptr, count)` is called with it. This is functionally equivalent to "frame_base + offset" (a root is still found by one arithmetic step from something computed once at frame-push time) but expressed as "array of already-resolved root addresses" rather than "one base plus a list of offsets to add to it" — necessary because this compiler's per-slot-alloca codegen shape has no single base address to offset from. The exact same path-walking logic (`gc_reference_paths`), applied instead with compile-time constant GEPs (`const_field_offset`), also produces the *byte-offset* table baked into each class's static descriptor for the heap-object field walk design D6 asks for — so the two places that needed "offsets" (frame roots, heap object fields) ended up with the representation each one could actually support, sharing one path-collector so they cannot drift apart.
- [x] 2.4 Emit `zirk_rt_pop_frame()` immediately before lowering every `Terminator::Return` to LLVM `ret` (design D2 — confirmed the only function-exit terminator this IR has).
- [x] 2.5 Codegen tests confirming the emitted IR/LLVM module has exactly one push per function entry and one pop per return path (including a function with multiple `return` statements/early returns).
  - `crates/zirk-codegen-llvm/tests/emission.rs`: `function_entry_pushes_exactly_one_gc_frame`, `every_return_path_pops_its_own_gc_frame` (three `return` statements, three pops, one push), `a_reference_typed_local_is_pushed_as_a_gc_root` (bonus: also confirms, end to end through real codegen, that D4's synthetic spill produces a second root alongside the named local — two roots, not one, for `mut p = Point(1)`). All pass.

## 3. Runtime (zirk-runtime) — collector core

- [x] 3.1 New module (e.g. `crates/zirk-runtime/src/collector.rs`, matching this crate's existing per-concern layout): the frame stack (`zirk_rt_push_frame`/`zirk_rt_pop_frame`, design D2) — a simple linked list or growable array of `(descriptor, frame_base)` pairs, matching function call/return nesting.
  - Implemented as a `thread_local! RefCell<Vec<Frame>>` (`Frame { roots: *mut *mut c_void, count: usize }`), not an intrusive list threaded through the native call stack: `push_frame`/`pop_frame` already happen in exactly the LIFO order a plain `Vec` push/pop already gives for free, so there was no correctness or performance reason to hand-roll a linked list instead. Follows this crate's existing `thread_local!`/`Cell` precedent (`exceptions.rs`'s `PENDING`).
- [x] 3.2 The intrusive all-allocations list: `zirk_rt_alloc` (grown, task 3.3) links every new allocation onto it via the header's `next` field (design D1).
- [x] 3.3 Grow `zirk_rt_alloc`'s body (`memory.rs`): track live-byte count; when a configured threshold is crossed, call the collector (task 3.4) before serving the new allocation; initialize the new object's header fields (descriptor as today, `next`/size per task 1.1/2.1's decision).
  - Threshold is 1 MiB of live bytes by default, overridable via the `ZIRK_GC_THRESHOLD` env var (bytes) — the mechanism section 4's low-threshold e2e fixtures use to force a collection deterministically without needing a program that actually allocates a megabyte.
  - Design note not anticipated by `design.md`: every collector allocation is pinned to a **fixed** 16-byte alignment (`GC_ALIGN`), not `requested.max(GC_ALIGN)`. Design D1 stores only `size` in the header, not the alignment a class asked for; without storing alignment too, `sweep`'s `dealloc` has no way to reconstruct anything wider than one constant both ends already agree on. 16 bytes covers every alignment this compiler's types can currently demand (the widest is `Float128`); a `debug_assert!` in `allocation_align` would catch the day that stops being true, rather than silently under-aligning. `zirk_rt_alloc` also floors `size` itself at the 3-word header size (`HEADER_BYTES`) regardless of what is requested — every real, codegen-driven allocation already clears that floor on its own (`object_struct` always emits the header as its first fields), but `register` unconditionally writes into header words 1 and 2, so nothing may be served smaller than that without writing past the allocation.
- [x] 3.4 Mark phase (design D6): walk the frame stack (task 3.1); for each root, if non-null and unmarked, mark it (set the low bit of `next`) and recurse into its own managed-reference fields via its layout (reuse whatever layout-walking mechanism already exists for casts/dispatch, e.g. the same descriptor-driven approach `zirk_rt_check_cast` uses, extended to walk fields rather than just ancestors).
- [x] 3.5 Sweep phase (design D6): walk the `next`-linked all-allocations list; `dealloc` (using the header's stored `size`) anything unmarked and unlink it; clear the mark bit on survivors for the next cycle.
- [x] 3.6 Runtime unit tests (mirroring `memory.rs`'s existing `#[cfg(test)]` style): a synthetic object graph with a cycle collects correctly (both objects reclaimed once unreachable); an object reachable only through a pushed frame survives a collection; an object no longer reachable after a frame pops is reclaimed on the next collection; the threshold trigger actually fires a collection at the configured point and not before.
  - All four scenarios implemented in `crates/zirk-runtime/src/collector.rs`'s own `#[cfg(test)]` module, against hand-built synthetic objects (no codegen involved) exercising `mark`/`sweep`/`maybe_collect` directly. Passing, including under the default parallel test runner across repeated runs (`thread_local` state is per-OS-thread, and each test resets it first).
