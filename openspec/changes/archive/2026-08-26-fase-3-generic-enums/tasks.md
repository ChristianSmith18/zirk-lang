## 1. Checker (zirk-sema)

- [x] 1.1 Remove the `is_native` gate in `resolve_enum_reference` (`crates/zirk-sema/src/checker.rs`, ~line 4290-4305, design D1) — a generic enum instantiation is accepted for any enum, not just `Iteration<T>`/`Result<T,E>`. Confirm the surrounding constraint-checking logic (the loop just above the gate) already applies correctly regardless of which enum is being instantiated — it should, since it iterates the enum's own declared type parameters, but verify rather than assume.
  - Removing this gate alone was not sufficient: `declare_enum` (line ~3230) minted a generic enum's own type parameters through `enter_type_params`, which unconditionally reports `NOT_LOWERED` the first time any declaration's type-param span is seen — the same function a generic *function*/*method* uses, correctly, since those really aren't lowered. A class avoids this by minting its own ids through `mint_type_param_ids` instead (`register_class`) and only entering `enter_type_params` a second time (a no-op re-entry) once its members are checked. `declare_enum` had no equivalent two-phase split, so *every* user-declared generic enum was rejected at its own declaration, independent of the instantiation gate. Fixed by having `declare_enum` mint type-param ids the same way `register_class` does (push the scope frame, report variance, resolve constraints inline) instead of calling `enter_type_params`. This was a second, real scope-fence gate the proposal did not enumerate — narrow fix, same character as D1's own reasoning, not new mechanism.
- [x] 1.2 Checker unit tests: a simple single-type-parameter user generic enum instantiates and type-checks; a multi-type-parameter enum (`Either<L, R>`) instantiates correctly; constraint violations on a user generic enum's type argument are still rejected with the existing diagnostic (unchanged behavior, just no longer gated afterward). Added in `crates/zirk-sema/tests/typing.rs`: `valid_generic_enum_with_data_instantiates_like_a_native_one`, `valid_generic_enum_with_multiple_type_parameters`, `invalid_generic_enum_type_argument_violating_a_constraint_is_still_rejected`. The pre-existing `invalid_generic_enum_with_data_is_not_lowered_yet` was replaced (its premise no longer holds) rather than left contradicting the new behavior.

## 2. IR (zirk-ir) — verification, not new mechanism (design says this should mostly already work)

- [x] 2.1 Verify `specialize_enum` (`crates/zirk-ir/src/lower.rs`, ~line 752) correctly specializes a multi-type-parameter user enum (design D2's first case). Confirmed via IR test (2.4) and end-to-end fixture (3.2).
- [ ] 2.2 **BLOCKED — genuine gap found, not fixed.** A variant payload naming another generic instantiation (`enum Wrapper<T> { Inner(value: Option2<T>) }`) fails at the *checker* level, before `specialize_enum` is ever reached: both `Checker::infer_type_params` (~line 9723, the loop matching `Base::Param(id) = param.ty.base`) and `Checker::substitute` (~line 9813, used by `check_direct_call_with_subst_seeded` to compute expected argument/return types) only handle a parameter type that is *directly* `Base::Param` — neither recurses into a nested `Base::EnumInstance`'s own type arguments the way the *other* existing substitution function, `Checker::substitute_type` (~line 4320, used for contract method signatures), already correctly does. Concretely: constructing `Wrapper.Inner(Option2.Some2(9))` against an expected `Wrapper<Int32>` computes `param_ty = substitute(Option2<T>, {T: Int32})`, which returns `Option2<T>` unchanged (T still unresolved) since the top-level type is `EnumInstance`, not `Param` — producing `E0403: there is no implicit conversion from Option2<Int32> to Option2<T>`. This is a real limitation in the checker's generic-argument inference/substitution, shared by whatever else calls these two functions (not enum-specific), and fixing it means teaching two argument/return-type-facing functions to recurse the way `substitute_type` already does elsewhere — a change to shared generic-inference machinery, judged out of this task's "verify, don't build" scope. Reported per design's own instruction to stop and report rather than build a workaround.
- [ ] 2.3 **BLOCKED — different gap than anticipated, found before `specialize_enum` is reached at all.** A self-referencing enum (recursive, generic or not) cannot even be *declared* today: `declare_enum` resolves every variant's associated field types in the same pass that registers the enum's own name in `self.enums` (the push happens only at the very end of `declare_enum`), so a variant payload naming the enum's own type (`Node(value: T, left: Tree<T>, right: Tree<T>)`) fails to resolve with `E0402: unknown type: Tree` — confirmed with both a generic (`Tree<T>`) and a plain non-generic recursive enum (`enum IntList { Nil, Cons(head: Int32, tail: IntList) }`), so this is **not specific to genericity or to `specialize_enum`'s memoization** as design D2/risk section assumed — no self-referencing enum of any kind reaches `specialize_enum` today. A class avoids this by registering its name+arity (`register_class`) *before* any field is resolved (`declare_class_members`, a later pass); `declare_enum` has no equivalent two-phase split. Fixing this would mean splitting enum declaration into a name-registration pass and a field-resolution pass, verifying the split does not break the several other checker passes that currently assume `declare_enum` fully populates an enum in one call — judged a structural change beyond this task's scope. Reported per design's own instruction (D1 risk mitigation: "if `specialize_enum` does not already memoize correctly, this is a blocking finding to report") — the finding is blocking for the same reason, one layer earlier than anticipated.
- [x] 2.4 IR-level tests for the two shapes that do work (2.1 and the un-blocked half of D2), each with an explicit assertion that only one `EnumLayout` is produced per distinct instantiation. Added in `crates/zirk-ir/tests/lowering.rs`: `a_user_generic_enum_instantiated_twice_produces_two_independent_layouts`, `a_user_generic_enum_named_twice_at_the_same_type_reuses_one_layout` (memoization/dedup, confirmed via the checker's own `intern_enum_instance` structural-equality interning, which runs before `specialize_enum` ever sees `checked.enum_instances`), `a_multi_type_parameter_user_enum_specializes_both_parameters`. No test added for 2.2/2.3's shapes since they do not compile at all (see above).
