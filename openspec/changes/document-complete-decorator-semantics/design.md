## Context

Zirk reserves `fn dec` for validated compile-time metaprogramming, but its current documentation mixes an early target-block model, optional runtime reflection, metadata retention, constructor targets, and loosely described transformations. The accepted language direction instead needs a deterministic model that is statically typed, permission-aware, incrementally cacheable, source-mapped, suitable for framework generation, and fully erased after compilation.

The design must support framework patterns comparable to NestJS, Spring Boot, FastAPI, and Angular without making framework concepts such as modules, controllers, components, records, interfaces, enum cases, or constructors into language-level decorator targets. Those roles can be expressed by class, member, callable, and parameter decorators that generate ordinary typed registries and descriptors.

## Goals / Non-Goals

**Goals:**

- Define one coherent declaration, target, phase, wrapper, dependency, repeatability, and erasure model.
- Keep every compiler-provided value explicit in a pattern or target-block binding.
- Preserve public callable and object contracts unless an allowed additive transformation is explicitly requested.
- Make expansion deterministic, permission-safe, hygienic, incrementally cacheable, and diagnosable at original source locations.
- Support statically generated framework registries, validation, serialization, routing, dependency injection, lifecycle hooks, authorization, logging, caching, and similar patterns.
- Update all public documentation to the same English source of truth.

**Non-Goals:**

- Implement the compiler phases in this documentation change.
- Add general `comptime {}` execution or expose the compiler's private AST.
- Retain decorator identity or arguments automatically at runtime.
- Add decorator targets for modules, abstract classes, interfaces, traits, records, value classes, enums, enum cases, or constructors.
- Add properties or accessors; Zirk continues to use attributes and conventional `get_`/`set_` methods.
- Allow decorators to replace arbitrary declarations, weaken visibility, remove effects, or bypass type checking.

## Decisions

### 1. Decorators are typed compile-time declarations

`fn dec` declares a non-repeatable decorator and `repeatable fn dec` declares a decorator whose contiguous applications are processed as one ordered group. Decorators are not ordinary runtime function values and are removed after validated expansion. The compiler preserves only ordinary declarations, wrappers, descriptors, and registries explicitly generated by the decorator.

This is preferred over automatic runtime metadata because framework discovery, routing, injection, serialization, and validation can be compiled into typed static structures with less binary size, less startup work, and stronger compile-time diagnostics.

### 2. Zirk 1.x has five decorator targets

The supported target blocks are `class`, `attribute`, `function`, `method`, and `parameter`. A parameter target also includes initialization parameters. A method target can inspect bodyless abstract, interface, or trait signatures but can wrap only a method that has an implementation.

Framework-level concepts remain library roles: for example, `@Module`, `@Controller`, `@Component`, and `@Entity` are class decorators rather than separate target categories. Attribute decorators cover fields stored by classes, records, and value classes. Constructor-specific work is expressed through initialization parameters, attributes, generated factories, or a class decorator.

### 3. Expansion uses explicit typed target blocks and phases

A decorator contains one block per supported target. Each target block receives a typed immutable target handle. Transformations are selected through:

```zirk
match target.transform {
    Inspect(context) => { ... }
    Augment(builder) => { ... }
    Wrap(wrapper) => { ... }
}
```

The compiler completes all applicable `Inspect` work before committing mutations, then applies `Augment`, and finally `Wrap`. `Inspect` may validate and emit metadata or diagnostics, `Augment` may add compatible declarations or contracts, and `Wrap` may wrap executable targets. All generated syntax returns through resolution, typing, effect analysis, and validation.

### 4. Wrapper behavior uses the established `match` model

Inside `Wrap`, executable behavior is selected through `match target.wrap` with `Before()`, `After(result)`, `After(result, transform)`, `Catch(error)`, or `Around(next)`. `Around` controls the entire invocation and cannot ambiguously coexist with the other wrapper variants in one decorator application.

`After(result)` observes a result. `After(result, transform)` receives a compiler-provided, non-escaping, one-shot transform capability that may replace the result with a compatible value. `Void` callables use `After()`. `Catch(error)` may rethrow exactly, throw another declared or inferred error, or recover with a compatible result; it cannot erase `throws` unless exhaustive analysis proves recovery. Wildcard payload patterns such as `After(result, _)` are valid and retain exact variant arity.

### 5. Wrappers preserve callable identity and visible effects

A wrapper automatically preserves the target name, visibility, parameters, labels, defaults, variadics, generics, constraints, return type, receiver mutability, override slot, documentation, source map, and callable identity. It cannot silently narrow permissions or errors. Any additional error or permission effect introduced by expansion is visible to normal inference and diagnostics.

### 6. Source order follows mathematical composition

Decorator expressions are evaluated top-to-bottom. The closest decorator is the innermost wrapper, so:

```zirk
@Authorized()
@Cached()
fn report() -> Report { ... }
```

composes as `Authorized(Cached(report))`. This matches the familiar TypeScript/Python composition model.

### 7. Declarative dependencies validate but never reorder source

Decorator declarations may use optional `requires decorators [...]`, `before decorators [...]`, and `after decorators [...]` clauses. They express required presence or essential relative order between different decorator declarations. If source order contradicts a constraint, compilation fails with a suggested source reordering; the compiler never silently changes composition.

Self-reference in any of the three clauses is invalid. The dependency graph also rejects direct and indirect cycles and reports the complete cycle. Same-decorator cardinality and ordering belong to repeatable-application inspection, not dependency clauses.

### 8. Repeatable applications are explicit grouped payloads

Contiguous uses of a `repeatable fn dec` are grouped into one logical expansion in source order. They are not nested independent copies. Every phase that needs the group binds it explicitly:

```zirk
match target.transform {
    Inspect(context, applications) => { ... }
    Augment(builder, applications) => { ... }
    Wrap(wrapper, applications) => { ... }
}
```

`applications` is immutable and typed as the ordered applications of that decorator. A loop binding introduces each `application`, and arguments are accessed through typed names such as `application.arguments.name`. The decorator decides whether equal applications are combined, ignored, warned about, or rejected. Repeatable applications must be contiguous so grouping remains local and visually obvious.

### 9. Generated syntax is hygienic and public conflicts are errors

Compiler-private generated bindings receive hygienic identities and cannot collide with user names. Creating a public declaration or member requires an explicit builder operation. A collision between user code or multiple decorators is a compile-time error; there is no implicit priority or last-writer-wins behavior.

Generated public API participates in documentation, interface emission, compatibility checking, language-server results, reflection descriptors explicitly generated by the framework, and source mapping.

### 10. Expansion is bounded, deterministic, and incrementally cached

Generated declarations are not decorated automatically. Explicit generated decorator applications enter a subsequent bounded expansion round. The compiler detects repeated structural expansion and reports a cycle before reaching its hard round/resource limits.

An expansion fingerprint includes the decorator implementation and version, arguments, typed target, relevant configuration, granted build permissions, observed files/environment/network/process inputs, and transitive dependencies. Unchanged fingerprints reuse validated results; changed inputs invalidate only affected expansions.

### 11. Effects use the existing build-permission model

Decorator argument evaluation and expansion may perform an external effect only when the final application grants the corresponding operation with `during: build` or `both`. A dependency cannot grant itself authority. Every observed value becomes a tracked build input. Secret values are redacted and cannot leak through source, generated public structure, IR, diagnostics, logs, or cache keys.

### 12. Generic, inheritance, and override behavior is declaration-based

A decorator expands once on a generic declaration and the validated generated form specializes normally. Zirk 1.x does not run decorators independently for every monomorphization.

A decorated inherited method retains its wrapper when it is not overridden. An overriding method does not inherit the decorator automatically and must reapply it explicitly. Class-level additive contracts follow normal class/interface/trait validation and cannot create silent implementation obligations.

### 13. Diagnostics preserve origin and expansion provenance

Decorators may emit `target.error`, `target.warning`, and `target.note`, each attached to a concrete target or decorator-argument span. Errors in generated syntax identify the generated declaration, decorator application, target, and actionable original location. Decorators cannot suppress compiler errors.

### 14. Runtime reflection is not automatic

There is no `runtime fn dec` form and no general `Reflection.decorators(target)` API in Zirk 1.x. When runtime information is needed, the decorator explicitly generates an ordinary typed descriptor, member, or registry. This retains only framework-required data and remains visible to normal typing, permissions, dead-code elimination, documentation, and compatibility analysis.

## Risks / Trade-offs

- **[Static generation cannot inspect completely unknown future plugin types]** -> Keep runtime descriptors library-defined and revisit a narrow opt-in metadata facility only after a demonstrated use case cannot be solved by generated registries.
- **[Dependency clauses add grammar and graph complexity]** -> Restrict them to different decorators, preserve source order, reject cycles, and keep all clauses optional.
- **[Repeatable grouped expansion differs from nested decorator intuition]** -> Require contiguous applications, preserve source order, expose an explicit typed `applications` payload, and document grouping with normative examples.
- **[Powerful augmentation can destabilize public APIs]** -> Limit operations to validated additive builders, reject conflicts, and emit generated API through standard documentation and compatibility tooling.
- **[Build effects can undermine reproducibility or expose secrets]** -> Reuse signed build permissions, fingerprint every observed input, redact secrets, and fail closed when inputs or authority cannot be verified.
- **[Multi-round generated decorators could loop]** -> Use structural cycle detection plus strict expansion round and resource limits.

## Migration Plan

1. Publish `zirk-decorators` and the grammar delta as the normative contract.
2. Rewrite the metaprogramming handbook section and tutorial around the accepted declaration, phase, repeatability, dependency, and erasure model.
3. Update the language/compiler/stdlib specifications, template notes, permission pages, toolchain pages, reference pages, and source map to remove old target and runtime-retention claims.
4. Add cross-document examples for validation, HTTP routing, dependency injection, wrapper composition, repeatable middleware, generated registries, diagnostics, permissions, generics, and overrides.
5. Run repository documentation checks, link checks, OpenSpec strict validation, and searches for contradictory terminology.

Rollback consists of reverting the documentation and delta artifacts; this change does not mutate compiler behavior or user data.
