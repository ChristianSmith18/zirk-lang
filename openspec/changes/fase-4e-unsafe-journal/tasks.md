## 1. Runtime (zirk-runtime)

- [x] 1.1 New module `journal.rs`: `zirk_rt_journal_begin() -> *mut Journal` (allocates an undo log, not collector-tracked — same category as the frame stack), `zirk_rt_journal_record(journal, address: *mut u8, len: usize)` (snapshots `len` bytes at `address` into the log before the write it guards executes), `zirk_rt_journal_commit(journal)` (discards the log without restoring, frees the journal itself), `zirk_rt_journal_rollback(journal)` (restores every recorded snapshot in reverse order, then discards/frees).
- [x] 1.2 Runtime unit tests: record then commit leaves memory unchanged and frees the log; record then rollback restores the original bytes; multiple records to different addresses roll back all of them in reverse order; multiple records to the *same* address roll back correctly to the original pre-block value (not an intermediate one) given reverse-order restoration.

## 2. IR (zirk-ir)

- [x] 2.1 Add journal IR instructions: `JournalBegin`, `JournalRecord(address, len)`, `JournalCommit`, `JournalRollback`.
  - **Representation note**: split into `JournalRecordSlot { journal, slot }`/`JournalRecordField { journal, object, index }` rather than one `JournalRecord(address, len)` — codegen resolves the address (`alloca`/GEP, exactly like `Store`/`StoreField` themselves do) and the byte length (`BasicTypeEnum::size_of`, the same idiom `InstKind::Alloc`'s own size already uses) from the slot/field's own static type, so the IR never needs a separate address-of step or a `Pointer<T>` type for the address operand.
- [x] 2.2 Lower `unsafe { ... }`: `JournalBegin` on entry. Before every `Store`/`StoreField` inside the block whose target is a managed slot/field declared *outside* the block, emit `JournalRecord` before the store. A slot declared inside the block itself is not journaled. On the block's normal fall-through exit, emit `JournalCommit`.
  - **Scope refinement**: the "declared outside the block" exemption applies to `Store` (a slot) only, tracked by comparing the slot's id against a `slot_boundary` snapshot of `self.slots.len()` taken at the block's own `JournalBegin` — IR-lowering already allocates slot ids in strict lexical/lowering order, so this is equivalent to (and simpler than) reusing the checker's own scope tracking, and correctly treats a synthetic GC-spill slot's declaring position as wherever its own `declare_slot` call happens to run, matching design D1's own note. `StoreField` has no such exemption (a field is heap state, not lexically scoped) — every `StoreField` inside an active, uncommitted `unsafe` block is journaled unconditionally, an accepted minor over-journaling.
- [x] 2.3 Lower `commit { ... }`: at commit's own entry, emit `JournalCommit` against the *enclosing* `unsafe` block's journal (durably publishing everything journaled so far), before lowering commit's own body normally.
  - **Correctness addition beyond the literal task wording**: the enclosing `unsafe` block's own frame is marked `committed` at that point, so (a) its own normal-exit `JournalCommit` is suppressed (avoiding a double-free of the same handle), (b) further writes inside the same block after `commit {}` are no longer journaled (matching "commit publishes writes before the irreversible effect" — post-commit writes are not reversible), and (c) the rollback-on-exception path (2.4) skips an already-committed frame.
- [x] 2.4 Rollback-on-exception: reuse the existing pending-exception check point (`lower_throws_check`'s mechanism). If the pending-exception slot is set, emit `JournalRollback` instead of `JournalCommit`, then let propagation continue exactly as it already does.
  - **Design refinement found necessary during implementation**: a pending exception inside an `unsafe` block never reaches the block's own post-`lower_block` code — `lower_throws_check`'s branch diverts control into `lower_pending_exception_dispatch` directly, which never returns to that point. The actual correct hook is therefore inside `lower_pending_exception_dispatch` itself, not "immediately before the block's own normal-exit `JournalCommit`" as literally written. Implemented by interleaving `try_stack` and a new `unsafe_stack` by a shared monotonic push-order counter (`pushed_at` added to both `TryFrame` and the new `UnsafeFrame`), so the dispatch walks both in true lexical nesting order: a `try`/`catch` nested inside an `unsafe {}` block that covers the exception is tested (and, on a match, stops the walk) *before* that block's own journal is even considered, and `Scope::Unsafe` frames roll back (unconditionally, since the decision is static, not a runtime branch) exactly when the walk reaches them uncaught. This is what makes `try { ... } catch (...) { ... }` nested inside `unsafe { ... }` correctly *not* roll back when the exception is handled locally — a case the literal task wording did not consider but that the merged design implicitly requires for correctness.
  - **Documented, accepted limitation**: an early `return`/`break`/`continue` exiting an `unsafe` block (not an exception) does not commit that block's journal — the handle is leaked (not corrupted, not rolled back incorrectly), since `run_finally_through`'s own try-only mechanism was not extended to unsafe frames. No task in this change's own test list (4.1–4.5) exercises this path; flagged here as the natural next refinement rather than worked around silently.
- [x] 2.5 IR-level tests: an `unsafe {}` block with a managed write lowers to `JournalBegin` → `JournalRecord` → (write) → `JournalCommit` on the normal path; a `commit {}` inside an `unsafe {}` block emits `JournalCommit` at commit's own entry against the outer journal (and exactly once — not a second time at the unsafe block's own fall-through); a write to a slot declared inside the `unsafe` block itself does NOT get a `JournalRecord`; the exception-pending check point correctly branches to `JournalRollback` instead of `JournalCommit`. (`crates/zirk-ir/tests/lowering.rs`, "`unsafe { }`/`commit { }` journal" section.)
