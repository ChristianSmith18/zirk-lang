Structured by default

Concurrency and parallelism

Zirk separates waiting from computation: tasks express concurrent lifetimes, threads expose OS execution, and parallel blocks use a managed multicore pool.

Tasks and awaiting

task creates work owned by a lexical scope. await suspends the current task without blocking its worker thread. A parent scope does not finish while child tasks remain, and cancellation flows down the task tree.

structured tasks
task profile = fetch_profile(user_id);
task activity = fetch_activity(user_id);
render(await profile, await activity);

Zirk uses no async fn marker: suspension is visible where await occurs and described by the callable contract.

Channels

Channel<T> communicates typed values with bounded or unbounded capacity. Closing a channel is observable; send/receive operations are cancelable. Bounded channels provide backpressure rather than unbounded memory growth.

Parallel work

multicore work
parallel for image in images {
    image.resize(width: 640);
}

parallel and parallel for schedule CPU work on a managed pool. Captured mutable state must be proven safe or protected with sync or Atomic<T>. Ordering is not implicit.

Threads and synchronization

thread creates a real OS thread and returns a joinable typed handle. Use it for explicit affinity or blocking native integrations, not routine asynchronous I/O. Mutex<T>, read/write locks, semaphores, barriers and atomics live under std.sync; memory order is explicit where relevant.

Cancellation and timeouts

Cancellation is cooperative and has a typed reason. Waiting operations, I/O and timers are cancelable. Timeouts compose at the call site:

timeout
inmut response = await client.get(url) timeout 5s;

Resource scopes close before cancellation leaves them. Detached work is not the default and cannot silently outlive application ownership.

Scheduler model

A reactor handles asynchronous I/O while a scheduler runs tasks. HTTP does not allocate one thread per request. CPU-heavy handlers move explicitly into parallel. This division keeps blocking visible and prevents event-loop control from leaking into user code.
