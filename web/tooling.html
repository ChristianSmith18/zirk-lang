Compiler and tooling

Parsing, types, diagnostics, formatting, linting and editor intelligence share persistent structures. LLVM is invoked only when native code is needed.

Compiler pipeline

source to native
.zrk source → incremental lexer → syntax tree
→ module/name resolution → type + flow analysis
→ validated decorators → typed portable IR
→ LLVM IR → object → Mach-O / ELF / PE binary

The semantic AST is private. Tools and decorators use a public, immutable, versioned Syntax API. Portable typed IR supports generic specialization, devirtualization, escape analysis, safety checks, vectorization and debug information.

Diagnostics

compiler diagnostic
error[E1234]: incompatible branch type
  src/users.zrk:18:12
   |
18 |     Error(error) { 0 }
   |                    ^ expected String, found Int32
   |
   = cause: every match branch must produce a compatible type
   = help: return a String from this branch

Every diagnostic has severity, stable code, source location, cause and actionable help when a clear repair exists. Decorator failures map generated code back to both expansion and original source.

Formatter, linter, LSP and debugger

The formatter is canonical, idempotent and intentionally avoids style-fragmenting options. It writes semicolons and normalizes whitespace and braces. The linter shares parsed and typed state; automatic fixes must be safe and reviewable.

The LSP provides completion, hover, navigation, references, rename, semantic tokens, signatures, formatting and code actions using cancelable incremental snapshots. Debug information maps breakpoints, stepping, variables, stacks, threads, tasks and channels back to .zrk.

Tests and benchmarks

test commands
zirk test --unit
zirk test --e2e --jobs 8
zirk test --tag database --seed 420
zirk test --report json
zirk bench

Compiler validation includes lexer/parser suites, diagnostic snapshots, type and safety cases, IR/codegen by target, ABI tests, incremental/reproducible builds, formatter idempotence, fuzzing and debug/release differential tests. Each language rule needs at least one valid and one invalid case.
