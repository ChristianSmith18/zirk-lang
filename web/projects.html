Projects and packages

A Zirk project makes its shape, targets, dependencies, globals and permissions visible in one declarative manifest.

Project layout

application tree
my-app/
├── init.zrk
├── zirk.lock
├── src/
│   ├── main.zrk
│   └── domain/user.zrk
└── test/
    └── users.e2e.zrk

Files are modules. Declarations remain file-local unless published with share. Quoted relative imports omit the extension; standard-library and package modules use symbolic unquoted names.

init.zrk

The manifest is a dedicated DSL, not executable code and not a place for global imports or arbitrary compiler configuration.

init.zrk
project {
    name: "weather-service";
    type: application;
    version: "1.0.0";
}
build_targets { x86_64-linux; aarch64-macos; }
permissions {
    network { connect: ["api.example.com:443"]; }
    filesystem { read: ["./config"]; }
}
compile_permissions { filesystem { read: ["./schema"]; } }

Runtime and compile-time capabilities are separate. The narrowest declared scope wins; missing access produces an explicit diagnostic or typed runtime error.

Globals

Only an application may declare globals, inside globals in init.zrk. Each consumer explicitly opts in with use NAME. Mutable globals used by parallel or thread require sync or Atomic<T>.

application globals
globals {
    inmut APP_NAME: String = "Weather";
    mut REQUEST_COUNT: Atomic<UInt64> = Atomic(0);
}

Dependencies and packages

zirk add, remove, install and update manage dependencies. A .zpkg contains a manifest, public API, portable typed IR, license and documentation. Implementation IR is lowered for the application's target, so core, runtime, stdlib, dependencies and application share one ABI.

zirk.lock records exact versions and hashes. zirk update deliberately recalculates resolution; normal locked builds do not drift.

Targets and reproducibility

Target selection resolves from --target, then manifest build_targets, then host detection. The initial matrix covers Windows, Linux and macOS across supported x86, x86_64, armv7 and aarch64 combinations. SDK, linker and native dependency availability still constrain cross-compilation.

Cache keys include source content, compiler version, target, relevant flags, dependency API, IR version and configuration. Given the same source, lockfile, toolchain and target, release artifacts intended for distribution must reproduce.
